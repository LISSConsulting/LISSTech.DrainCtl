1. Installation

DrainCtl ships as a single MSI. Deploy it however you deploy software — N-central, SCCM, Intune, GPO, or just double-click it.

Silent install

msiexec /i LISSTech.DrainCtl.msi /qn

What the MSI does

  • Installs drainctl.exe and drainctl.dll to C:\Program Files\LISS Technologies\LISSTech DrainCtl\bin\
  • Adds the bin folder to system PATH — drainctl is available immediately in any terminal
  • Registers the LISSTech.DrainCtl PowerShell module in C:\Program Files\WindowsPowerShell\Modules\
  • Creates the data directory at C:\ProgramData\LISS Technologies\LISSTech DrainCtl\
  • Installs and auto-starts the DrainCtl Windows Service (runs as LocalSystem)
  • Registers the Event Log source with a custom message file
  • Writes default configuration to the registry
💡 No reboot required. The service starts immediately. Open a new terminal and drainctl check will work right away.

Silent uninstall

msiexec /x LISSTech.DrainCtl.msi /qn

This stops the service, removes all files, cleans up PATH, and deregisters the Event Log source. Your audit data in ProgramData is preserved (delete it manually if you want a clean slate).

2. First Run

After installation, verify everything is working:

# Is the service running?
Get-Service DrainCtl

# Quick status check (instant — talks to the service via named pipe)
drainctl check

# PowerShell way
Get-RDSHDrainMode | Format-List

You should see status=Healthy and connections_allowed=true. If drain mode is active on this server, you'll see the current state and how long it's been active.

⚡ Instant response? If drainctl check responds in under 100ms, it's talking to the service over the named pipe. If it takes a second or two, the service isn't running and it's falling back to a direct registry read. Check Get-Service DrainCtl.

3. Configuration

All settings live in the registry and hot-reload automatically when you change them. No service restart needed.

HKLM\SYSTEM\CurrentControlSet\Services\DrainCtl\Parameters
ValueTypeDefaultWhat it does
GracePeriodDWORD60Minutes drain mode must be active before it becomes an alert. During the grace period, the status is "Grace" and exit code is 0.
RetentionDaysDWORD90Days to keep audit records. Maximum 365. Older records are pruned daily.
PollIntervalDWORD300Seconds between safety-net polls. The service also uses real-time registry notifications, so this is a fallback.
AuditPathSZProgramData pathFull path to the JSONL audit trail file.
WebhookURLSZemptyWebhook endpoint for push notifications.
NtfyURLSZemptyntfy.sh topic URL for push notifications.
NotifyOnTransitionDWORD1Send notification when drain mode changes (on or off).
NotifyOnGraceExceededDWORD1Send notification when drain mode exceeds the grace period.
NotifyRepeatMinutesDWORD0Re-send alert notifications every N minutes while in alert state. 0 = notify once.

You can edit these with regedit, reg.exe, GPO preferences, or PowerShell:

# Set grace period to 2 hours via PowerShell
Set-ItemProperty -Path "HKLM:\SYSTEM\CurrentControlSet\Services\DrainCtl\Parameters" `
    -Name "GracePeriod" -Value 120 -Type DWord

The service picks up the change within seconds (it watches the Parameters key with RegNotifyChangeKeyValue).

4. Audit Setup (Change Attribution)

DrainCtl can tell you who changed drain mode — but it needs Windows to record that information first. Run this once (as admin):

drainctl audit-setup
# or
Install-RDSHDrainAudit

This does two things:

  1. Enables the Registry audit subcategory via auditpol
  2. Sets a SACL on the Terminal Server registry key so that Windows writes Event ID 4657 whenever TSServerDrainMode is modified
⚠️ Domain-joined machines On domain-joined servers, Group Policy refresh (~90 min) can overwrite local auditpol settings. For persistence, configure the equivalent GPO:

Computer Configuration > Policies > Windows Settings > Security Settings > Advanced Audit Policy Configuration > Object Access > Audit Registry > Success

Without audit setup, DrainCtl still detects changes instantly — it just can't tell you who made them. The changed_by field will be empty.

5. CLI Usage

Check current state

# Plain text (default — great for terminal and N-central)
drainctl check

# JSON (great for parsing)
drainctl check --format json

# Table
drainctl check --format table

# Quiet mode (only final status line)
drainctl --quiet check

View audit history

# Last 50 records (table format)
drainctl history

# Only state transitions
drainctl history --changes-only

# Last 10 records as JSON
drainctl history --limit 10 --format json

Exit codes

CodeMeaningWhen
0Healthy / GraceConnections allowed, or drain mode active but within grace period
1AlertDrain mode active beyond grace period — new connections are blocked
2ErrorRegistry unreadable or other failure

Output formats

--format plain (default for check), table (default for history), csv, json.

6. PowerShell Module

The module is auto-registered by the MSI. It works on both PowerShell 5.1 and 7+.

# Rich status object
Get-RDSHDrainMode

# Boolean check — perfect for scripts and alerts
if (Test-RDSHDrainMode) { "All good" } else { "ALERT: drain mode active!" }

# Audit history
Get-RDSHDrainHistory -Limit 20

# Only transitions (who changed what, when)
Get-RDSHDrainHistory -ChangesOnly | Format-Table Timestamp, DrainMode, ChangedBy

# Pipeline magic
Get-RDSHDrainHistory -ChangesOnly |
    Where-Object { $_.DrainMode -ne "ALLOW_ALL_CONNECTIONS" } |
    Select-Object Timestamp, ChangedBy, DrainMode

7. Notifications

Get pushed when something happens. DrainCtl supports webhooks (any HTTP endpoint that accepts JSON) and ntfy.sh (open-source push notifications for your phone).

Setup

# Webhook (Slack, Teams, PagerDuty, custom endpoint, etc.)
drainctl notify set-webhook https://hooks.slack.com/services/T.../B.../xxx

# ntfy.sh (get push notifications on your phone!)
drainctl notify set-ntfy https://ntfy.sh/my-rdsh-alerts

# Check what's configured
drainctl notify status

# Send a test to make sure it works
drainctl notify test

PowerShell way

Set-RDSHDrainNotification -WebhookURL "https://hooks.example.com/drainctl"
Set-RDSHDrainNotification -NtfyURL "https://ntfy.sh/my-alerts"
Test-RDSHDrainNotification

# See current config
Get-RDSHDrainNotification

What triggers notifications?

EventRegistry valueDefaultExample
State transitionNotifyOnTransitionOnAdmin runs chglogon /drain — you get pinged
Grace exceededNotifyOnGraceExceededOnDrain mode active for 61 minutes (grace=60) — alert fires
Repeat alertsNotifyRepeatMinutes0 (once)Set to 30 to get re-alerted every 30 min while in alert

Webhook payload

{
  "event": "transition",
  "host": "MDS-LDC1-RDS5",
  "drain_mode": "ALLOW_RECONNECTIONS_PREVENT_NEW_LOGONS",
  "previous_mode": "ALLOW_ALL_CONNECTIONS",
  "status": "Grace",
  "message": "Drain mode active, within grace period (45m remaining).",
  "changed_by": "MDS\\lissadmin",
  "state_duration_seconds": 900,
  "timestamp": "2026-04-03T14:30:00-04:00"
}

ntfy messages arrive with priority high for alerts (red notification on your phone) and default for transitions.

8. N-central Integration

DrainCtl was built for N-central. The AMP (Automation Policy) just runs drainctl check and thresholds on the exit code.

How it works

  1. N-central agent runs the AMP at its polling interval
  2. AMP executes drainctl check
  3. DrainCtl connects to the service via named pipe — instant response
  4. AMP captures stdout (structured key=value lines) and the exit code
  5. N-central thresholds: exit code 0 = Normal, 1 = Failed
🎯 Pro tip: Even if N-central only polls every 15 minutes, the service detected the change in real time. The audit trail has the exact timestamp and attribution. N-central is just sampling the service's state.

Minimal AMP script

drainctl check --quiet
exit $LASTEXITCODE

That's it. --quiet suppresses intermediate log lines — only the final status line is emitted, which N-central captures.

9. Service Management

The MSI handles service installation. These commands are for manual management or troubleshooting.

# Check service status
Get-Service DrainCtl

# Stop / Start / Restart
Stop-Service DrainCtl
Start-Service DrainCtl
Restart-Service DrainCtl

# Manual install (if not using MSI)
drainctl service install
drainctl service start

# Manual uninstall
drainctl service stop
drainctl service uninstall

What the service does

  • Subscribes to registry changes on TSServerDrainMode via RegNotifyChangeKeyValue — instant detection
  • Subscribes to Security Event ID 4657 via EvtSubscribe — knows who made the change
  • Polls every 5 minutes as a safety net
  • Maintains an in-memory audit store (flushed to JSONL every 30 seconds)
  • Serves queries over a named pipe (\\.\pipe\drainctl) for instant CLI/PS responses
  • Writes to the Windows Event Log (Application/DrainCtl) on state changes
  • Sends webhook/ntfy notifications when configured
  • Hot-reloads configuration when registry parameters change

Event Log

Check Application log, source DrainCtl:

IDLevelWhat happened
1000InfoService started
1001InfoService stopped
1002InfoCheck: healthy
1004InfoState transition detected
2000WarningDrain mode in grace period
3000ErrorDrain mode alert (grace exceeded)

10. Troubleshooting

"changed_by" is empty

Run drainctl audit-setup as admin. On domain-joined machines, also configure the GPO (see Audit Setup).

Service won't start

Check the Application Event Log for DrainCtl errors (Event ID 3002). Common causes:

  • Another instance holds the audit file lock — restart the machine or find the process
  • Permissions on the ProgramData directory

CLI is slow (1-2 seconds instead of instant)

The service isn't running. drainctl check falls back to direct registry read + file-based audit. Start the service: Start-Service DrainCtl.

Notifications not arriving

  1. drainctl notify status — verify URLs are set
  2. drainctl notify test — sends a test message
  3. Check the Application Event Log for "webhook notification failed" or "ntfy notification failed" warnings
  4. Verify network connectivity from the RDSH server to the webhook/ntfy endpoint
