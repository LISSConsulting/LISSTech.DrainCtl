# Feature Specification: Fleet Sessions (012)

**Feature branch**: `012-fleet-sessions`
**Created**: 2026-09-26
**Status**: Draft
**Scope**: An administrator-only, current-state fleet Sessions dashboard, machine-authenticated session snapshots, privacy-controlled session detail, and safe agent-executed session actions.

## Problem and product boundary

Operators can see aggregate RDS session counts today but cannot answer which users are active, disconnected, idle, consuming CPU or memory, or which process is responsible. They also need a safe route to log off or message an exact live session without a session-ID reuse mistake. This feature adds that operational view without introducing RD Broker as a runtime dependency or turning session data into long-lived telemetry.

The authoritative identity is **`(canonical_host, uint32 session_id)`**. Every side-effecting action additionally binds the session's expected **`logon_at_ms`**. A different logon time means the numeric ID was reused; the action MUST fail without calling WTS.

## Evidence and fixed decisions

- The agent already enumerates current WTS sessions in `sessions.go`; the dashboard already has durable host state, machine-authenticated report ingestion, SSPI user sessions, SSE, SQLite/WAL, settings delivery, confirmations, toasts, and a brutalist expandable-table precedent in `ServerTable.svelte`.
- WTS is the source for user/domain, WTS state, station, client, and session timestamps. The agent is the source for live CPU, working set, input delay, and per-session top processes. RD Broker data is neither queried nor required.
- Session detail is **current-only**. SQLite retains only the latest host/session snapshot for stale/offline visibility and privacy-deletes it at the configured retention deadline; this feature creates neither charts nor a session-history table.
- The existing heartbeat endpoint has a 64 KiB compatibility contract. The new snapshot travels independently on a dedicated machine-authenticated endpoint with a hard 512 KiB decoded-body limit.

## User stories and acceptance scenarios

### US-1 — Find a host or session in the fleet (P1)

As an administrator, I can open **Sessions** from primary navigation and search, filter, sort, and page a bounded fleet roster to locate sessions without loading personal/process details for every host.

**Independent test**: seed host summaries across states and verify a Sessions admin can use every toolbar control; verify a non-admin cannot see the tab or retrieve either session API.

1. **Given** an authenticated administrator, **when** the dashboard loads, **then** it displays the Sessions primary tab alongside Overview, Servers, and Events, a fleet table, host summary metrics, and the mockup's sticky header/footer treatment.
2. **Given** more results than a response page permits, **when** a user changes page or sort, **then** the client sends the bounded query, renders that page, and does not manufacture omitted rows.
3. **Given** a query matching canonical host or numeric session ID, or a user value when `identity_visibility=full`, **when** the user submits search, **then** matching host summaries are returned; a host summary contains no username, client, or process payload. With masked or hidden identity, the same control continues to search host/ID but MUST NOT retain a clear user value solely to make user search possible.
4. **Given** All, Active, Disconnected, or Idle is selected, **when** results load, **then** host summaries match its documented aggregate-state predicate and the selected pill has the accessible selected state.
5. **Given** an admin selects a sortable mockup column, **when** sort changes, **then** the order is deterministic with canonical host as final tie-breaker and the header exposes its `aria-sort` value.

### US-2 — Inspect one current host snapshot (P1)

As an administrator, I can expand one host to see its latest current WTS sessions and live performance, including explicit capability, stale, empty, and collection-error states.

**Independent test**: ingest a complete snapshot containing active, idle, and disconnected sessions and bounded process lists; fetch the expanded host; then test disabled collection, absent agent capability, stale snapshot, empty snapshot, and an agent collection error.

1. **Given** a host row with a usable snapshot, **when** it is expanded by mouse, Enter, or Space, **then** the UI fetches `GET /api/v1/sessions/{host}` and renders the host aggregate strip (TOTAL, ACTIVE, IDLE, DISCONNECTED), per-host session search, and columns **ID, USER, STATE, CLIENT, LOGON TIME, IDLE, CPU, MEM, APP, PROCESS, Shadow**.
2. **Given** no sessions in a valid complete snapshot, **when** expanded, **then** the panel says no current sessions and does not show prior rows.
3. **Given** snapshot collection is disabled, unsupported, failed, stale, or has intentionally hidden/masked fields, **when** displayed, **then** the respective status is explicit and no missing datum is represented as zero, healthy, or an empty current snapshot.
4. **Given** an expanded host has up to 500 current sessions, **when** the administrator searches or pages within it, **then** filtering/paging is local to the returned bounded current payload and does not issue unbounded fleet requests.
5. **Given** a session contains a null/unavailable metric, **when** rendered, **then** its cell is an em dash or documented unavailable marker, not `0`.

### US-3 — Receive and retain only complete current snapshots (P1)

As the server, I retain the last successful complete snapshot from a machine account while recording every newer collection attempt, so host detail remains coherent and stale attempts cannot overwrite newer state.

**Independent test**: POST valid, oversized, malformed, same-instance old/equal-sequence, a greater UUIDv7 new generation, a delayed old generation after that new generation commits, empty, over-count, unknown-schema, and fatal collection-error snapshots; verify latest-attempt metadata, last-success rows/counts, the durable generation fence, and host summary transactionally.
1. **Given** a machine-authenticated agent POSTs a complete `drainctl.session-snapshot.v1` with its durably reserved service-start UUIDv7 `agent_instance_id`, canonical-decimal-string `sequence:uint64`, and `logical_cpu_count` 1–1024, **when** its decoded request is at most 512 KiB and meets every structural bound, **then** the server replaces that host's session rows and last-success summary in one SQLite transaction and records the same instance/sequence, observation, and receipt as its latest attempt. The stored summary is `session_count`; `active_count` for `active|connected`; `idle_count` for `idle`; `disconnected_count` for `disconnected`; `user_count` for distinct non-null projected `(user,domain)` pairs (zero when identity is hidden); and `last_activity_at_ms` as the maximum non-null input/connect/logon activity.
2. **Given** a valid snapshot from the stored `agent_instance_id` whose `sequence` is less than or equal to the stored latest-attempt sequence, **when** accepted structurally, **then** the server performs no mutation and returns `202 {"accepted":false}`. A different UUIDv7 instance starts a generation only when its parsed 16-byte value is strictly greater than the durable per-host fence; the same transaction advances that fence and accepts its sequence reset. A different instance equal to or lower than the fence is stale, even when delayed after a newer generation committed. `observed_at_ms` is diagnostic only; UUID text locale order is never used.
3. **Given** a valid newer successful empty snapshot, **when** ingested, **then** it atomically clears every current row for that host and records a zero-count last-success snapshot.
4. **Given** a valid newer fatal WTS collection-error snapshot, **when** ingested, **then** it records the newer attempt instance/sequence, receipt/status/error and preserves the prior last-success rows, counts, identity, observation, and receipt; only a newer successful complete empty snapshot may clear them.
5. **Given** more than 500 sessions, more than 5 processes in a session, an invalid state/number/timestamp, invalid UTF-8, an overlength bounded string, invalid canonical decimal string, CPU above `100 * logical_cpu_count`, bytes above SQLite `MaxInt64`, unknown schema version, mismatched path/body host, or a body over 512 KiB, **when** posted, **then** the server returns a 4xx error and changes no stored session data.
6. **Given** snapshot receipt succeeds, **when** the server updates the current host view, **then** it emits an additive metadata-only `session_snapshot` SSE envelope containing canonical host, instance/sequence identifiers as canonical decimal strings, last-success aggregate summary, latest-attempt receipt/status, and no user/client/process/identity payload. The current broker broadcasts this safe metadata event to authenticated subscribers; non-admin clients ignore it and cannot call Sessions APIs. An expanded admin UI refetches its host endpoint on that event.

### US-4 — Respect privacy and retention (P1)

As a privacy-conscious administrator, I can configure which administrator-visible identity, client, and process fields are full, masked, or hidden, while old snapshots are deleted promptly.

**Independent test**: configure each visibility mode, ingest representative values, verify storage/API/UI transformations and audit redaction; change a visibility policy and verify immediate snapshot purge/cascading detail removal, durable fence preservation, and safely cancelled/expired actions; advance the cleanup clock past retention and verify the fence remains.

1. **Given** `identity_visibility`, `client_visibility`, or `process_visibility` is `full`, `masked`, or `hidden`, **when** snapshots are persisted and returned, **then** the configured projection is applied before SQLite persistence and response construction; hidden values are absent, masked values use one deterministic documented mask, and `full` preserves the bounded collected value. Any visibility-policy change immediately privacy-deletes all `session_snapshots` and cascading `session_latest` rows, but retains `session_generation_fence`; active actions are safely cancelled or expired, and loosening cannot reconstruct prior data or let an old generation reclaim the host.
2. **Given** a snapshot reaches `last_success_received_at_ms + retention_hours`, **when** cleanup runs in bounded batches, **then** it deletes that host snapshot and cascading current rows but retains `session_generation_fence`. Pending action delivery remains available through its five-minute action expiry; terminal outbox, audit, and agent-ledger records remain until their independent action-relative cutoff.
3. **Given** a session action is audited, **when** audit records are written or queried, **then** they include actor, action type, canonical host, numeric session ID, expected logon time, command ID, request/outcome timestamps, and result code, but never username, domain, client, process, message text, or snapshot payload. Snapshot retention is independent: terminal outbox, audit, and agent-ledger records remain until each action-relative retention cutoff, even after a snapshot purge.

### US-5 — Safely act on an exact session (P1)

As an administrator, I can launch a safe local Shadow session with a command-copy fallback, or explicitly confirm a disconnect/logoff/message that the agent executes at most once against the session instance I reviewed.

**Independent test**: issue duplicate action requests, delivery retry, expiry, reused session ID, WTS failure, and success paths against a fake clock/WTS adapter; inspect the audit projection.

1. **Given** the host is an RFC 1123 hostname and the row has a numeric session ID, **when** Shadow is selected, **then** the UI requests the endpoint-owned `drainctl-shadow://shadow?host=<host>&session=<id>` URI and navigates to it only after exact client validation; it retains an accessible copy fallback for `mstsc.exe /v:<host> /shadow:<id> /control`. The GUI helper validates the complete URI before launching local mstsc with fixed arguments. Any origin may invoke the registered protocol; normal browser/Windows external-protocol confirmation and mstsc consent remain, and `/noConsentPrompt`, credentials, arbitrary arguments, and server-side launches are prohibited.
2. **Given** `sessions.allow_actions=false`, stale/offline/unknown/unsupported host capability, or a session without valid expected logon time, **when** an administrator views the row, **then** Disconnect, Log Off, and Send Message are disabled with an explanatory reason; Shadow remains available only when its input is safe.
3. **Given** actions are enabled and a fresh actionable session exists, **when** an administrator chooses Disconnect, Log Off, or Send Message, **then** a modal names the host, numeric ID, and action, and for message the exact bounded message text; keyboard focus is trapped and restored; only explicit confirmation queues the action.
4. **Given** the same authenticated actor retries the same action at the same endpoint with the same client-generated idempotency key and normalized request fingerprint within its action lifetime, **when** the endpoint receives it, **then** it returns the existing command/outcome rather than queueing a second WTS operation; the same key with a different request returns a conflict.
5. **Given** a newly queued or previously delivered nonterminal action, **when** the agent next receives its normal report response before five minutes elapse, **then** that response may redeliver the same command ID, subject to the 20-action response maximum. The agent durably claims it before WTS, never re-executes a claimed ID after restart, compares expected and actual logon time before its first execution, reports a safe terminal/duplicate outcome in its next report, and the dashboard updates durable status/audit/SSE without PII.
6. **Given** delivery is not completed by expiry, **when** five minutes pass, **then** the server marks the command expired and never delivers it thereafter.

## Functional requirements

### Configuration and authorization

- **FR-001**: Add a `sessions` configuration block with defaults: `enabled=true`, `collect_processes=true`, `top_processes=3`, `retention_hours=24`, `allow_actions=false`, and each of `identity_visibility`, `client_visibility`, `process_visibility`=`full`.
- **FR-002**: Validation MUST restrict `top_processes` to integer 0–5, `retention_hours` to integer 1–168, and visibility values to `full|masked|hidden`; rejected settings MUST leave effective configuration unchanged.
- **FR-003**: The settings GET MAY expose nonsecret `SessionsConfig` to authenticated users. Mutation of `allow_actions`, privacy, or any Sessions setting MUST require a dashboard administrator and distribute collector-relevant values to remote agents through existing remote-settings/report machinery. Any visibility-policy mutation immediately privacy-deletes `session_snapshots` and cascading `session_latest`, safely cancels or expires active actions, and MUST retain `session_generation_fence`.
- **FR-004**: `AuthInfo`, login/session state, and `/api/v1/me` MUST expose an authoritative `is_admin` boolean. Group membership resolution remains server-side; a browser-provided role is never trusted.
- **FR-005**: Every Sessions data route and action endpoint MUST require an authenticated admin (403 for authenticated non-admin; 401 for unauthenticated). The client MUST hide Sessions navigation and must not initiate session requests for non-admins.

### Snapshot contract and persistence

- **FR-006**: `POST /api/v1/session-snapshot` MUST require machine authentication and use a separate request body limit of 512 KiB; it MUST NOT loosen the existing 64 KiB `/api/v1/report` limit.
- **FR-007**: Snapshot schema name is exactly `drainctl.session-snapshot.v1`. Its versioned payload contains a UUIDv7 `agent_instance_id` generated and durably reserved at agent service start, per-instance incrementing `sequence:uint64` encoded as a canonical unsigned decimal JSON string, `host`, `observed_at_ms`, `collector_version` (UTF-8 1–64 bytes, no controls), `logical_cpu_count` integer 1–1024, collection capability/status/error code, aggregate fields, and 0–500 sessions for a successful complete attempt. Each session has `session_id:uint32`, `logon_at_ms`, bounded WTS metadata, `state` in the documented set including `unknown` (which the UI renders after known states), nullable live metrics, and 0–5 bounded process entries. Browser/API `working_set_bytes` fields are canonical decimal strings.
- **FR-008**: Canonicalize and validate host identity at machine-auth/path boundaries. The authenticated machine principal must be authorized for the canonical body host; the API never uses an uncanonicalized value as a database key, route target, SSE key, or command target.
- **FR-009**: A newer successful complete snapshot is a complete host replacement: it updates `session_snapshots` last-success fields, replaces wide `session_latest` rows, and transactionally persists `session_count`, active (`active|connected`), idle, disconnected, distinct projected non-null user/domain, and last-activity aggregates. A newer fatal collection-error attempt updates only `session_snapshots` latest-attempt fields and preserves last-success rows/counts. It MUST contain no EAV table and no historical per-session table. `processes_json` stores only the already-projected bounded current process list.
- **FR-010**: Schema version 4 MUST migrate transactionally and retain existing data. Its six v4 tables are five dashboard telemetry tables—`session_generation_fence`, `session_snapshots`, `session_latest`, `session_action_outbox`, and `session_action_audit`—and the agent-local `session_action_ledger`; agent-local startup also uses `session_generation_fence` to reserve its UUIDv7. Required indexes support fleet host lookup/sort/filter, idempotency, expiry/status lookup, and retention deletion. The exact canonical DDL is [data-model.md](./data-model.md); no other specification duplicates it. The service composition root creates the telemetry stores, injects dashboard-facing interfaces into `dashboard.NewSubsystem`, and starts/stops/retains them safely; handlers never own session persistence.
- **FR-011**: At agent startup, the local telemetry DB MUST durably reserve a UUIDv7 strictly greater than its per-host `session_generation_fence` using parsed 16-byte comparison. The dashboard applies a snapshot transactionally: for the same instance, only a strictly newer sequence is accepted; for a different instance, only a UUIDv7 strictly greater than the durable dashboard fence starts a new generation and advances that fence; a lower/equal different UUIDv7 is stale. UUID strings MUST NOT be locale-compared. The fence survives snapshot retention and privacy purges, so no old generation can reclaim a host. `session_snapshots` stores latest-attempt and nullable last-success instance IDs plus sequence alongside observation/receipt timestamps. Last-success rows/counts describe only the last successful complete snapshot. Freshness is `unknown` without last success; otherwise `offline` when the host registry is off or age exceeds `10 * heartbeat`, `stale` when age exceeds `3 * heartbeat`, and `fresh` otherwise. It uses last-success server receipt; `observed_at_ms` remains display/diagnostic only. A latest fatal error is separately `collection_status:error`.
- **FR-012**: A periodic cleanup MUST privacy-delete expired snapshots in bounded transactions and be safe to resume after restart, without deleting or reducing `session_generation_fence`. Action expiry is independently action-relative: pending actions expire at five minutes, while terminal outbox/audit/agent-ledger records remain until their own action-retention cutoff, irrespective of snapshot purge.

### Query and live-update contract

- **FR-013**: `GET /api/v1/sessions` returns a bounded fleet host-summary envelope only. It supports validated `q`, `state=all|active|disconnected|idle`, `sort`, `dir=asc|desc`, `page`, and `page_size` (15, 30, or 50); its response includes applied query, total count, page metadata, and no identity/client/process fields. `q` matches canonical host and numeric session ID in every privacy mode; it matches stored user identity only when `identity_visibility=full`, and MUST NOT introduce a retained clear-text search index for masked/hidden identity.
- **FR-014**: Fleet summaries MUST expose canonical host, last-success session aggregates, last-success instance/sequence and observation/received timestamps, latest-attempt instance/sequence and observation/received timestamps, freshness (`fresh|stale|offline|unknown`) computed from last-success receipt, latest collection capability/status/error code, host state/mode, and a `detail_available` flag. Their deterministic sort whitelist is `host`, `status`, `mode`, `sessions`, `active`, `idle`, `disconnected`, `users`, and `last_activity`.
- **FR-015**: `GET /api/v1/sessions/{host}` returns one canonical host's latest complete snapshot and at most 500 current session rows. It accepts only validated local presentation pagination/search parameters; it returns 404 for unknown/expired session data, 403 before existence disclosure to non-admins, and explicit data state rather than fabricated rows.
- **FR-016**: Both GET endpoints MUST set no-store cache controls. Their handler read must use a bounded SQLite operation timeout and return a typed unavailable response on database failure.
- **FR-017**: SSE `session_snapshot` is additive, metadata-only, and safe for the current all-authenticated broker broadcast; non-admin clients ignore it and cannot call Sessions APIs. `session_action` is likewise privacy-safe status-only. The frontend stores action status in `sessionStorage`, polls `GET /api/v1/session-actions/{action_id}` every two seconds until terminal, aborts polling on navigation/terminal state, resumes after reload, and maps terminal status to a toast. Snapshot events do not make current snapshot data authoritative in the browser: admin clients refetch expanded detail and discard an out-of-order response only when it has an equal/older sequence from the same instance; a different instance is a refetch generation change. Retain explicit error/stale state on refetch failure.

### Agent collection and Windows APIs

- **FR-018**: Session metadata MUST use documented WTS APIs: `WTSEnumerateSessionsW`, `WTSQuerySessionInformationW` for user/domain/state/station/client/times, `WTSFreeMemory`, `WTSLogoffSession`, and `WTSSendMessageW`. Session 0/listener/service pseudo-sessions are excluded by the existing WTS selection rules.
- **FR-019**: Per-session PDH metrics MUST use named counters and strict numeric PDH instance-to-session-ID matching; names that merely contain the ID do not match. Collect CPU, working set, input delay, and available RemoteFX values; unavailable counters remain null and do not fail a snapshot.
- **FR-020**: Process accounting MUST enumerate through Toolhelp, map PIDs with `ProcessIdToSessionId`, open query-only limited handles, calculate CPU from creation-time baselines and deltas normalized by transmitted logical CPU count, and release every handle each cycle. It MUST retain no process handle or prior process identity beyond the collection needed for a delta. The canonical agent process has numeric `pid:uint32`, nullable CPU, and `working_set_bytes:uint64`; per-process CPU is nullable for a first or inaccessible delta. Storage/API projection retains PID and metrics, masks only `image_name` as `***` in masked mode, and returns an empty process list in hidden mode.
- **FR-021**: Top processes MUST be deterministic and bounded by configured `top_processes`, using fixed-size heap selection rather than sorting an unbounded process collection: CPU descending (null last), working set descending, image name case-insensitive ascending, then PID ascending.
- **FR-022**: The agent MUST send snapshots independently of the legacy heartbeat and MUST tolerate dashboard 404/405/413/schema rejection as a feature-local diagnostic while preserving its existing report loop.

### Action contract

- **FR-023**: `POST /api/v1/sessions/{host}/{session_id}/actions` accepts a body with exactly `type` and `expected_logon_at_ms`, plus optional `message`. Unknown keys are rejected. `type` is only `disconnect`, `logoff`, or `message`; `expected_logon_at_ms` is required; `message` is required, nonempty, and 1–256 Unicode scalar values after trim for `message`; for `disconnect` and `logoff` it is permitted only when empty. A UUID idempotency key is required. Message text is never put into SSE, audit, logs, or returned after queue acknowledgement.
- **FR-024**: Action enqueue MUST atomically validate current host/session/action capability/freshness, normalize and hash the request, enforce the durable `(requested_by, endpoint, idempotency_key)` scope, and reject a matching key with a changed request fingerprint as conflict. It MUST persist the opaque protected message payload only for message, durable action metadata/status, and an append-only audit event. The endpoint returns `202` for newly queued and `200` for same-request idempotent replay.
- **FR-025**: A report response MAY include up to 20 additive `pending_session_actions` for its authenticated host, and accepts up to 20 terminal completion records. Queued and delivered nonterminal commands remain eligible for same-ID delivery until terminal/expiry. Before WTS, the durable local `session_action_ledger` records `claimed`; it never re-executes a claimed command after restart, compares expected and actual logon time before its first execution, reports a safe terminal/duplicate outcome in its next report, and the dashboard updates durable state/audit. Disconnect invokes `WTSDisconnectSession(..., false)`; it never accepts or sends message content.
- **FR-026**: Durable action state is `queued`, `delivered`, `completed`, `failed`, `expired`, `session_changed`, or `unsupported`. Repeated delivery and completion reports are idempotent; a terminal command is never executed again.

## Nonfunctional requirements

- **NFR-001 Scale**: Ingestion is bounded to 500 sessions × 5 processes and 512 KiB per host. Fleet queries return a maximum 50 summaries; host current detail returns a maximum 500 rows. No UI, API, or database query may materialize an unbounded fleet session set.
- **NFR-002 Performance**: Snapshot replacement is O(session count + process count), process selection is O(process count × log(top_processes)), and uses no retained process handles. One incoming snapshot causes at most one metadata-only SSE envelope. Server-side indexed host replacement/query and bounded body decoding prevent fleet size from multiplying individual agent work. Browser-facing sequence and byte counts are canonical unsigned decimal strings; no JavaScript number loses their precision.
- **NFR-003 Availability**: Snapshot and action failures cannot stop heartbeat reporting or host health. Snapshot database failure preserves prior complete rows. An optional PDH/process failure produces a successful row with null metric/capability false; a fatal WTS enumeration/metadata failure or collector timeout is visible but does not clear last good rows unless a valid newer complete snapshot says empty.
- **NFR-004 Accessibility**: Tablist, controls, filter pills, table header sort, expand/collapse, action buttons, dialog labels/descriptions, live toasts, focus order/trap/restore, Escape, Enter/Space behavior, visible focus, screen-reader table caption/scope, and reduced-motion behavior MUST meet existing dashboard patterns. Dense tables scroll horizontally inside their region on narrow screens and expose a visual/accessibility hint; the page body must not acquire a forced desktop minimum width.
- **NFR-005 Privacy/security**: Bounded strings are UTF-8-safe; user, domain, client, image, app, and process values are never logged in server ingest/action errors, SSE, fleet summaries, or audits. Message payload is encrypted/protected at rest using the product's existing protected-secret mechanism and is deleted at terminal completion or expiry. No RD Broker DB credential, query, or fallback is introduced.

## Failure modes

| Condition | Required behavior |
|---|---|
| Agent pre-feature or dashboard pre-feature during rollout | Core `/report` stays compatible. New agent treats snapshot 404/405 as unsupported; old dashboard ignores additive report response fields. |
| Snapshot transport/JSON/schema/bound violation | Reject only snapshot; preserve prior current rows and heartbeat. Log code/count without PII/payload. |
| Equal/older sequence from same agent instance | Acknowledge idempotently; do not overwrite newer rows or emit an SSE event. |
| Different UUIDv7 generation | A strictly greater parsed 16-byte UUIDv7 advances the durable fence and starts a reset sequence generation; a lower/equal different UUIDv7 is stale, including delayed old snapshots after a newer commit. |
| Agent collection partially unavailable | Send a successful complete snapshot with explicit capability/status and null unavailable metrics; PDH/process unavailability is not fatal. |
| Host offline/stale/error | Compute freshness as unknown with no last success; offline when registry status is off or age is over ten heartbeats; stale over three heartbeats; fresh otherwise. Latest fatal error is separate and display precedence is offline, error, stale, fresh/unknown. Retain latest successful snapshot only until privacy retention; actions disabled unless fresh and error-free. |
| SQLite lock/error | Bounded handler timeout; snapshot returns 503; preserve old committed state; retry on next normal report/cleanup cycle. |
| Snapshot exceeds retention | Delete atomically/batched; queries return no detail rather than stale private data. Terminal action outbox/audit/ledger retention is independent. |
| WTS action target reused or gone | Agent reports `session_changed`/`failed`; never call disconnect/logoff/message for a different logon time. |
| Agent does not report command before five minutes | Server expires action; agent receiving an expired command must not execute it. |
| Duplicate browser request, delivery, or agent completion | Same principal/endpoint/key plus matching request fingerprint returns the existing command/status; changed request conflicts. At most 20 commands are delivered or reported per response. Delivered commands may be redelivered by ID until terminal/expiry; the durable local claimed/terminal ledger permits no second WTS call, including after restart. |
| PDH/process access denied/counter absent | Mark metric/process capability unavailable; do not synthesize zero or fail WTS snapshot. |
| Shadow target or endpoint URI is unsafe | Do not offer a launch. RFC 1123 host and uint32 ID validation is required before requesting Shadow; the UI only navigates to the exact endpoint-provided URI, and the local helper strictly validates it again. |

## Success criteria

- **SC-001**: Admin/non-admin route and navigation tests prove complete authorization separation, including 403 responses.
- **SC-002**: Snapshot contract tests prove all size/count/string/timestamp constraints, UUIDv7-only validation, durable local reservation, parsed-byte generation fencing, same-instance monotonicity, delayed old-generation rejection after a new-generation commit, fence retention across privacy/retention purge, canonical decimal strings, logical CPU/CPU/SQLite-byte limits, persisted aggregate semantics, atomic successful complete replacement, fatal-error preservation of last-good rows/counts/freshness, stale-idempotency, and valid empty clear.
- **SC-003**: API tests prove fleet responses contain no PII/process fields, expanded responses respect all three privacy modes including masked process PID/metrics and hidden empty process list, `202 accepted:true|false`, and snapshot/action SSE contains no PII/process payload.
- **SC-004**: Deterministic retention tests delete session snapshot/current rows at every configured boundary (1 and 168 hours) without deleting the generation fence or a valid unexpired action, while independently preserving terminal outbox/audit/ledger until their action-relative cutoff.
- **SC-005**: Windows adapter tests prove strict PDH numeric matching, optional PDH/process nonfatal null/capability behavior, no retained handles, transmitted logical-CPU CPU normalization, deterministic fixed-heap top-N selection, and `unknown` state acceptance/render ordering.
- **SC-006**: Action tests prove always-mounted admin route/`sessions_disabled`, strict body rejection, confirmation gating, same-request replay, changed-request conflict, five-minute expiry, 20-action delivery/completion bound, expected-logon-time protection, claimed-ledger restart suppression/same-ID redelivery, and audit redaction.
- **SC-007**: UI validation uses pure helper tests only where Node built-in is sufficient, plus the fully enumerated deterministic OMP/browser-driver quickstart smoke and build proof for every mockup surface: nav, counts, search, four filter pills, all host/session columns, expansion, capability/stale/error/empty states, endpoint-owned Shadow launch plus accessible command copy fallback, confirmed Log Off/Send Message, sessionStorage/poll/reload terminal toasts, pagination/sort, keyboard, ARIA, and narrow horizontal scrolling.

## Explicit non-goals

- No retained per-session charts, trend/history API, EAV telemetry model, or session history table.
- No RD Broker database dependency, broker reconciliation, or use of Broker as a fallback data source.
- No server-side or remote shadow launch, automatic launch without user activation, or consent bypass; `/noConsentPrompt` is prohibited. The installer-registered local protocol may be invoked by any origin and must validate its complete URI before fixed-argument mstsc execution.
- No bulk session action, disconnect action, reset action, password/account administration, or automatic policy response.
- No action availability for non-admins, stale/offline/unknown hosts, or sessions lacking expected logon time.
- No process command lines, executable paths beyond bounded display name, handles, credentials, session payloads, or message content in telemetry/SSE/audits/logs.
- No change to the current 64 KiB heartbeat payload, host health freshness semantics, or existing server/metrics APIs except additive response command handling.
