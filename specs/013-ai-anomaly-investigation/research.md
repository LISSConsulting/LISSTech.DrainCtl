# Phase 0 Research: AI Anomaly Investigation

## Purpose

This document binds implementation of the optional OpenAI reasoning-investigation path and the deterministic central session-drop detector. It implements the revised feature specification and the OpenAI primary documentation: [Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs), [Responses create](https://developers.openai.com/api/reference/resources/responses/methods/create), and [Data controls](https://developers.openai.com/api/docs/guides/your-data). Existing detector, agent, notification, and storage behavior not expressly changed here remains unchanged.

---

## R1. Fixed OpenAI transport and informed consent

**Decision**: Implement one direct `net/http` profile, `openai_responses`: exactly `POST https://api.openai.com/v1/responses`, normal platform TLS validation (TLS 1.2+), redirects disabled, and exactly one `Authorization: Bearer <credential>` header. The provider client owns a dedicated production `http.Transport` with `Proxy:nil`; it never uses `ProxyFromEnvironment` or proxy credentials. The model is fixed to `gpt-6-astra`. There is no SDK, provider registry, custom endpoint/model, proxy URL, fallback, retry, URL credential/query/fragment, organization/project header, or remote-action capability.

Each foreground request is non-streaming and stateless: `store:false`, `background:false`, `stream:false`, `truncation:"disabled"`, `reasoning:{"effort":"high"}`, `max_output_tokens:8192`, `tools:[]`, `tool_choice:"none"`, and `parallel_tool_calls:false`. It has no conversation, `previous_response_id`, include list, encrypted reasoning/reasoning summary, polling, function, web, file, MCP, code, shell, computer, or other tool capability. One immutable attempt gets one transmission only.

Provider access and automatic investigation default to off. A settings `PUT` enables access only with the closed, server-verifiable acknowledgement object: `version:"openai_responses_privacy_v1"` plus exactly these eight Boolean members, all `true`: `third_party_subprocessors`, `no_training_without_opt_in`, `default_abuse_monitoring_up_to_30_days`, `store_false_application_state_only`, `temporary_prompt_cache_possible`, `zdr_mam_separate_approval`, `audit_days_local_only`, and `global_endpoint_no_regional_guarantee`. Unknown, missing, non-Boolean, or false clauses, and every other version, reject enablement. `investigation_privacy_acknowledgements` is append-only SQLite audit history with `id`, fixed version, authenticated actor, `accepted_at_ms`, and `clause_set_hash` (or a fixed complete-clause marker). The server validates every clause, appends that immutable audit row first, then atomically writes the config version and `privacy_acknowledgement_audit_id` that references it; a config-write failure may leave only a harmless unreferenced audit row. `acknowledged` derives true only when the config’s exact current version and referenced ID match an audit row. Migration, rollback, or rewrite clears/invalidates both version and audit ID. Retention removes unreferenced audit rows older than `AuditDays`, never the currently referenced row. `GET` returns only the safe version and derived `acknowledged`, never the eight Boolean clauses. The clauses respectively acknowledge OpenAI/subprocessors as third parties; no API training without explicit customer opt-in; default abuse monitoring up to 30 days; `store:false` application-state scope; possible temporary prompt cache; separate ZDR/MAM approval; local-only `AuditDays`; and no regional guarantee at the global endpoint.

**Rationale**: One fixed destination/model makes egress and consent auditable. The documented data controls distinguish application state, caching, abuse monitoring, and separately approved ZDR/MAM.

## R2. Central ownership, credential boundary, and operating setup

**Decision**: The dashboard/service alone owns provider configuration, evidence construction, attempts, Responses calls, and session-drop scoring. Agents retain `CheckResult`; `SpikePayload`, evtspike detection/notifications, agent report flow, CLI, PowerShell, installer, and machine configuration remain unchanged.

The encrypted OpenAI credential remains only in long-lived root `Config`/`config.json`. It is never a plaintext field of `Config`, `ServiceConfig`, `DashboardConfig`, `RemoteSettings`, closures, worker state, API DTOs, logs, SQLite, REST, SSE, or browser state. `internal/investigation` owns the sole narrow decrypt-for-send accessor: immediately after pre-send checks it decrypts into temporary bytes, constructs the HTTP request and its authorization header, then zeroes/releases those temporary bytes before the request result is handled. The accessor does not return a credential to callers or cache it. Existing atomic scoped config updates encrypt replacement material before persistence.

Every session-only provider-settings `PUT` requires exactly one credential command: `preserve`, `replace` with a non-empty value, or `clear`. Missing, null, empty, unknown, or conflicting commands are invalid and never imply preservation. Safe views expose only enabled/automatic/acknowledged state, acknowledgement version, and `has_credential`; they never return acknowledgement clauses, actor/time audit, or credentials. Provider fields are absent from `RemoteSettings` and machine `GET /api/v1/config`.

Privacy is closed by default: source, customer, user, and session identities, and arbitrary or nonfixed URLs, are forbidden from investigation evidence, results, attempts, provenance, and diagnostics. The only local-retention exceptions are the authenticated actor in `investigation_privacy_acknowledgements` for accountability and the fixed literal OpenAI endpoint in closed provenance. Neither exception egresses; both are governed by ACL and `AuditDays`.

Deployment guidance must be updated in `README.md`, `CLAUDE.md`, `docs/guide.html`, `internal/dashboard/openapi.yaml`, quickstart material, and API contracts. It must state LocalSystem as the supported service identity; machine-scope DPAPI ownership for the encrypted config; dashboard-group access as the only provider administrator/operator role; outbound TLS/firewall allowance only to `https://api.openai.com`; and provisioning, rotation (`replace`), preservation, and clearing of the write-only key. No support is claimed for a user-profile DPAPI key, agent key, alternate endpoint, regional endpoint guarantee, or plaintext environment/registry secret.

**Rationale**: This preserves current JSON/DPAPI ownership while making plaintext lifetime and external egress minimal and testable.

## R3. Bounded EvidenceV1 and request serialization

**Decision**: Build `EvidenceV1` as a typed object, field by field, from the existing versioned allowlist: source-relative ±30-minute window clipped at snapshot, source-only identity, deterministic omissions, and no generic map/raw struct/free text. It excludes host/FQDN/domain/IP/customer/user/session identity, `changed_by`, URL/path, Event Log/XML, dump, credential, notification secret, and arbitrary file content.

Select final visible units before assigning contiguous fact IDs: `window` (`F001`), `source` (`F002`), `context` (`F003`), retained local points, retained fleet points, then omissions. IDs are `F001`–`F134` only (three mandatory, at most 61 local, 61 fleet, and nine omissions). Source is `(source_kind, source_id)`; fleet labels are `peer_1`–`peer_60`; known channel codes or `custom_channel` replace arbitrary channel text.

Canonicalize the typed EvidenceV1 object to compact JSON. Enforce its 8,000 UTF-8-byte bound and the 16,384-byte completed request bound by removing the last fleet point, then last local point, then empty blocks while recording the relevant omission once and reallocating IDs. The canonical evidence bytes are appended **once** after the literal `EVIDENCE_JSON_V1\n` in `input_text`; outer request JSON serialization performs the only escaping. Evidence must never be pre-serialized as a JSON string and serialized again. A valid egress snapshot is `snapshot_kind=available` with strict EvidenceV1 and its facts. If mandatory evidence plus fixed schema/request overhead cannot fit, finalize a host-free `snapshot_kind=unavailable` snapshot with `canonical_json={}`, the SHA-256 of `{}`, and no fact rows; it is `state=insufficient_evidence`, `terminal_reason=evidence_unavailable`, with no result or provenance and no egress.

**Rationale**: Typed canonical evidence provides a bounded privacy allowlist and reproducible citations without double encoding.

## R4. Strict report, prose boundary, and local validation

**Decision**: Send the compile-time developer instruction plus exactly the evidence user item described in R3. The instruction calls evidence untrusted, requests read-only checks, limits citations to supplied fact IDs, and prohibits action execution. `check_type` constrains each suggested check to read-only intent. This is not a claim that natural-language prose can be perfectly classified as free of commands or remediation: the product guarantee is that all provider text is untrusted and is never executed, auto-linked, routed to a tool, or treated as authorization.

Use `text.format` `{type:"json_schema",name:"anomaly_investigation_v1",strict:true}` with every property required and `additionalProperties:false` at every object level. The report has exactly `result_version:1`, `summary`, `overall_assessment`, `evidence_sufficiency`, `human_review_required`, hypotheses, missing-evidence items, and `recommended_diagnostic_checks` (one to six sequential ranks). The report key is exactly `recommended_diagnostic_checks` in schema, model, storage, REST, SSE projections, tests, and UI. The strict schema fixes `summary` to `text_kind`, text, and 0–12 cited facts; hypotheses to rank/confidence/text kind/text/supporting and contradicting facts; missing-evidence items to category/text kind/text/related facts; and each recommended check to rank, read-only `check_type`, text kind/text, related hypothesis ranks, and related facts.
Every prose field has a strict schema pattern and local validation: valid UTF-8; trimmed; printable ASCII `0x20` through `0x7e`; U+0020 as its only whitespace; existing byte limits (summary 1,280, hypothesis/check 960, missing evidence 640); and no `/`, `\\`, `<`, `>`, `@`, backtick, CR, LF, or tab. Reject non-ASCII/control/format/surrogate/private/unassigned characters, forbidden punctuation, IPv4 or IPv6 literals, credentials, and case-insensitive ASCII-normalized substring containment of an excluded-identity canary. Canary matching is not whole-field equality. Do not claim to detect every invented hostname/domain that is neither evidence nor a configured canary.
Locally reject duplicate keys, trailing data, schema failure, unknown/duplicate cited IDs, contradictory/supporting overlap, missing/gapped ranks, nonexistent related-hypothesis rank, and invalid sufficiency cross-field rules. Insufficient reports require `overall_assessment=insufficient_evidence`, human review, no hypotheses, and missing evidence. Partial/sufficient reports require one to five hypotheses and a non-insufficient assessment. All accepted prose is persisted as bounded original escaped text with fixed `text_kind`; the exact adjacent labels are `Untrusted model hypothesis` and `Untrusted model-suggested diagnostic check`.

**Rationale**: Strict schema plus local lexical/structural validation makes the storage contract enforceable, while non-execution—not impossible semantic detection—is the safety guarantee.

## R5. Responses acceptance and failure mapping

**Decision**: Accept only 2xx JSON with identity/gzip encoding, headers at most 16 KiB, and a decompressed JSON body at most 32 KiB. Decode one duplicate-key-free envelope with no trailing data. Accept only `status=completed`, `error=null`, `incomplete_details` present and null, exactly one completed assistant message, and exactly one `output_text`; reasoning is ignored only when it includes no requested summary. Missing, non-null, or wrongly typed `incomplete_details`, and any tool/function/MCP/search/code/computer/shell item, are `response_invalid`.

`response_body_bytes` in provenance is the decompressed bounded JSON body byte count. The provider contract and closed provenance use only `send_authorized_at_ms` and `send_completed_at_ms` for send lifecycle; `request_started` and `request_completed`, and every other alias, are forbidden. Failed, refused, incomplete, invalid, and local pre-send-insufficient attempts have no provenance.

## R6. Durable lifecycle, storage failures, retention, and detector state

**Decision**: FR-006 pre-send persistence covers only attempt, source, lineage, and snapshot. Create those records transactionally before worker processing, marking `running`, or transmitting. A pre-send commit failure produces zero egress (FR-013); emit a structured local storage diagnostic and persist a terminal failure only if storage becomes writable without sending.

The global maximum is exactly 100 queued-plus-running attempts across every source. The root/retry creation transaction checks that limit before evidence assembly or attempt/evidence insertion for manual, retry, and automatic roots. A full interactive request returns `429 queue_full`; an automatic root creates zero work. Separately, the per-source retained-attempt cap is exactly 100 and is enforced transactionally for every root/retry, including an immutable local-insufficiency attempt. A further root or retry returns `409 attempt_limit_reached`; it never evicts retained history. This cap bounds the complete unpaginated attempt lineage returned by session-drop detail to 100, while general source history remains paginated.

`started_at_ms` means worker or cancellation processing began, not egress. A queue claim sets only `running` and `started_at_ms`; it creates no lease. Immediately before calling `Client.Do`, the worker atomically commits nullable `send_authorized_at_ms` and a 30-second `send_lease_expires_at_ms`; it means a provider transmission MAY have begun, never that the provider received it. Once non-null, it permanently forbids automatic resend. After the local HTTP exchange returns, the worker atomically commits `send_completed_at_ms`, clears the send lease, and sets the two-minute `finalization_lease_expires_at_ms`. `send_completed_at_ms` records only that local return and never proves provider receipt. A `running` attempt may have neither send timestamp. Local insufficiency, configuration cancellation, and request-limit cancellation terminalize with neither timestamp. Crashes are injected immediately after the authorization commit and immediately after transport return.

The fixed post-send finalization deadline is two minutes. After the local exchange returns and its terminal state cannot be written, discard the raw body, emit a storage diagnostic, retain at most one bounded in-memory validated terminal candidate, and retry only that SQLite finalization without resend while `finalization_lease_expires_at_ms` is active. At its deadline discard the candidate; once writable, finalize `failed/storage_unavailable`. No recovery payload is durable and no provider reconstruction or resend is permitted.

Startup and retention recovery run before ordinary `AuditDays` deletion. Retention MUST NOT delete evidence for a live `running` row while its applicable lease is active: the send lease before local transport return, or the finalization lease after it. Once no applicable lease remains active, recovery atomically terminalizes the row by the canonical restart/lease table: null `send_authorized_at_ms` becomes `failed/interrupted`; non-null authorization without a durable terminal becomes `failed/storage_unavailable`. Recovery neither reconstructs result/provenance nor resends. A queue claim requires `created_at_ms >= cutoff` and a valid persisted available snapshot/hash before it changes a row to running, so an expired queued attempt never egresses. `completed_at_ms` is null only for queued/running attempts and is set for every terminal attempt.

The local mandatory-evidence outcome uses the explicit unavailable snapshot: `snapshot_kind=unavailable`, `canonical_json={}`, SHA-256 of `{}`, and no facts; it is `insufficient_evidence/evidence_unavailable`, with no result/provenance. A provider-valid insufficient report has `state=insufficient_evidence`, empty terminal reason, validated result, and provenance. REST and SSE must distinguish those cases.

Use SQLite v4 additively with current WAL/ownership. Attempts are host-free and terminally immutable; their summary `terminal_reason` uses exactly the canonical closed attempt enum from the data model/provider contract—no stale aliases or transport/body-derived terms. Closed provenance contains only the fixed profile, fixed literal OpenAI endpoint, requested model, format/store flags, internal `send_authorized_at_ms`/`send_completed_at_ms`, request/response counts, and `validation_outcome`; it contains no identities, arbitrary URLs, response ID, returned model, headers, usage, reasoning, raw body/error/refusal text, or provider metadata. Deterministic session-drop source rows retain canonical host, which only authorized source/list/detail REST projections may resolve. SSE is one literal `data:` line containing the established `{type,host?,data,timestamp}` JSON envelope, with no named `event:` line. Investigation SSE payloads have no `host`. No raw/source free text enters investigation artifacts; source is kind/ID only, and validated bounded report prose is the sole free-text exception.

In the same SQLite writer transaction that accepts `servers.last_result_json`, insert an idempotent `session_drop_observation_inbox` row with `accepted_sequence INTEGER PRIMARY KEY AUTOINCREMENT` and `UNIQUE(canonical_host, report_epoch_ms)`. `accepted_sequence` is the private global acceptance order; `accepted_at_ms` is evidence/time only and is never an ordering key. The row records source-local offset/date, typed session-presence/counts, and the freshness, drain, and classification context needed for deterministic scoring. The accepted-report callback only wakes the consumer; it is not a correctness handoff. The detector drains strictly by `accepted_sequence` and atomically consumes a row with its watermark, baseline, and source updates, then deletes or marks that row consumed. On startup it drains pending inbox rows before newer reports are accepted. Permanent host removal deletes that host's pending inbox rows in its removal transaction. A crash after the acceptance commit but before the wakeup must drain exactly once at startup.

Each session-drop source persists central acceptance-time `confirmation_started_at_ms` and `confirmation_ended_at_ms`, separate from its report-epoch fields, and detail projects both without substitution. Each host baseline persists `last_normal_trained_at_ms`; only an eligible normal-training update advances it. The all-hours 24-hour readiness span is exclusively `first_trained_at_ms` through `last_normal_trained_at_ms`, never a decay, scoring, candidate, confirmation, drain, report-epoch, or acceptance timestamp.

Only permanent host removal clears session baseline/detector state transactionally. Offline, transient, unregistered, or other temporary states do not clear it. After active-lease protection and required running-row recovery, retain attempts independently by `attempt.created_at_ms < now-AuditDays`; retain session-drop source rows by `detected_at < now-AuditDays`, and baseline state until permanent host removal.

## R7. API/session-drop contracts and verification

**Decision**: Dashboard sessions authorize before any source lookup, evidence assembly, attempt creation, detail disclosure, or host resolution; machine accounts receive neither provider configuration nor investigation access. Authorization uses the login-time session's stored group snapshot and the atomically current configured dashboard group: the session must exist and its stored `Groups` must include that current group. It does not perform a live directory-membership lookup; external membership changes take effect on logout, expiry, or reauthentication. Session-drop routes use the common dashboard auth/error contract exactly: a missing or expired session is `401 {"error":{"code":"session_expired"}}`, dashboard-group denial is `403 {"error":{"code":"access_denied"}}`, and every error body is `{"error":{"code":"..."}}`. Only authorized source/list/detail REST projections resolve host. SSE, browser-local state, provider artifacts, and diagnostics remain host-free.

Before subscribing to shared `/api/v1/events`, and at every periodic revalidation, require that session-and-current-group predicate. After a successful `Dashboard.Group` configuration change, immediately invalidate every session and close all broker streams, requiring reauthentication; it cannot leave an old group subscribed. Tests cover a stale login-time group snapshot and a configured-group change closing streams.

The session-drop list/detail contract uses decimal IDs and cursors, closed objects, `next_before:null` on exhaustion, and `baseline_model_version`. The detail projects central acceptance times from the separately persisted `confirmation_started_at_ms` and `confirmation_ended_at_ms` exactly; these are distinct from the report-epoch fields. The list has **no attempt summary**. Detail always includes the complete retained immutable attempt summaries, capped at 100 by the per-source retained-attempt limit. Attempt REST objects expose lifecycle timestamps only as RFC3339 `created_at`, `started_at`, `send_authorized_at`, `send_completed_at`, and `completed_at`; SQLite/internal names retain `_ms`. OpenAPI fixes these shapes, exact authorization, query validation, canonical terminal-reason enum, and error rules; no alternative cursor or partial object shape is permitted.

Tests must prove the exact closed acknowledgement object (all eight named true clauses, rejected missing/unknown/false clauses, version migration, safe GET, immutable actor/time/clause-set audit, referenced-ID derivation, atomic config reference, and unreferenced-audit retention), decrypt-for-send plaintext lifetime/zeroing boundary, and explicit key commands. They must prove EvidenceV1 object-to-one-append serialization, available and unavailable snapshot forms, report key/prose/canary behavior, completed-only `incomplete_details:null` acceptance, status-only non-2xx mapping, decompressed provenance counts, exact fixed-endpoint/actor privacy exceptions with no egress, and hostile `HTTP_PROXY`/`HTTPS_PROXY`/`NO_PROXY` environments producing zero proxy connections. The proxy-isolation test constructs the actual production-owned transport/client and injects only its dial boundary; fake `RoundTripper` tests remain synthetic-response-only. Lifecycle tests prove authorization-marker and post-transport-return crash recovery, no resend after authorization, active send/finalization leases block deletion, expired leases atomically recover before `AuditDays` deletion, and both recovery table rows. Session-drop tests prove the durable inbox acceptance transaction, `accepted_sequence` assignment and strict drain ordering independent of equal/reordered `accepted_at_ms`, crash-after-commit-before-wakeup, startup drain exactly once, and permanent-removal inbox cleanup.

## R8. Rejected alternatives

**Decision**: Reject a session-drop list attempt summary because it can become an incomplete or divergent view of immutable lineage; detail is the sole attempt-summary surface. Reject named SSE events or a host-bearing investigation payload because both violate the established broker envelope and host-free investigation boundary. Reject connection-time-only shared-event authorization and live directory-membership lookup: authorization must instead compare the durable login-time group snapshot to the atomically current configured group at subscription and periodically; external membership changes require logout, expiry, or reauthentication. Reject retaining an accepted report only in a callback or in-memory queue because a crash can lose the detector observation; the durable inbox is the transactional source of truth. Reject environment proxy inheritance, proxy configuration, and proxy credentials because they create an unbounded egress route; the dedicated transport uses `Proxy:nil`. Reject durable retention of a post-send terminal result, transmission inference, provider reconstruction, or resend: authorization records only that a send MAY have started, and recovery finalizes safely without claiming receipt.

**Rationale**: These alternatives would weaken closed API shapes, auditable egress, crash-safe deterministic detection, session authorization, raw/provider-data minimization, or the evidence allowlist without providing required product behavior.

**Decision**: Phase 1 may proceed only with the above central-only, fixed-egress, DPAPI, durable-storage, host-free, no-action, and rollback boundaries. The recheck is evidence-backed: Constitution I is met by the Windows service/dashboard plan and unchanged CLI/PowerShell/installer; II by explicit unchanged surface assessment and additive session APIs; III by named unit, transport, SQLite, browser, installed-service, and final repository checks; IV by current JSON atomic/DPAPI flow plus v4 migration/rollback; V by durable safe diagnostics, authorized query paths, and SSE. Additional Constraints are met by concrete packages/docs, LocalSystem/DPAPI/firewall setup, retention/ownership, and Complexity Tracking. No exception is requested.
