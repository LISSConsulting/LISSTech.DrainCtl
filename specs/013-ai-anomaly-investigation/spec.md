# Feature Specification: AI Anomaly Investigation (013)

**Feature Branch**: `013-ai-anomaly-investigation`
**Created**: 2026-09-26
**Status**: Draft
**Scope**: Opt-in, evidence-bounded OpenAI reasoning reports for confirmed anomalies from existing evtspike events and a new deterministic lower-tail session-drop detector.

## Evidence boundary

This feature makes no new anomaly determination through a provider. Existing deterministic detectors remain the authority for whether an anomaly occurred. A confirmed anomaly starts an investigation only when the separately configured automatic-investigation option is enabled, or when an authenticated dashboard-group operator explicitly requests or retries it.

Only a bounded, versioned, structured allowlist DTO may leave the central service through the configured provider boundary. It is assembled field by field and may contain fact-ID-keyed source anomaly facts; retained aggregate metrics around the event; drain transitions; host freshness; detector status; and fleet temporal correlation. It MUST exclude canonical host names, FQDNs, domains, IP addresses, customer names, usernames, session identifiers, `changed_by`, free text, URLs, paths, generic maps, raw structs, Event Log messages or XML, crash dumps, credentials, notification secrets, and arbitrary files. Canonical host identity remains required in the durable deterministic source anomaly and MAY be displayed only by authenticated dashboard-group source/list/detail APIs.

Evidence facts use deterministic IDs `F001` through `F134`. Model-generated prose is untrusted data: it is bounded, validated, stored only after complete validation, rendered as HTML-escaped plain text, and never executed, routed to tools, or used to take action. The product does not claim that semantic prose validation can prove absence of commands or remediation: the developer prompt requests read-only checks, `check_type` constrains intent, and every report field is untrusted and non-executable. Recommended diagnostic checks are operator guidance only and are bounded, read-only descriptions; they are not commands, scripts, PowerShell, remediation, drains, restarts, notifications, configuration changes, or credential/file access.

## Clarifications

### Session 2026-09-26

- **Q: What is in scope, and which component owns analysis? → A:** Session-drop detection is in scope now. The central dashboard/service instance owns provider configuration, evidence assembly, provider calls, durable attempts, and central lower-tail scoring from distinct accepted reports; agents retain their existing `CheckResult` and `SpikePayload` contracts, receive neither provider keys nor provider calls, and existing evtspike behavior remains unchanged.
- **Q: Which provider and consent model are supported? → A:** Provider access and automatic analysis are separately off by default. Enabling access requires the server-verifiable closed `openai_responses_privacy_v1` object with exactly eight all-true boolean clauses. The authoritative acknowledgement is an append-only SQLite audit row with version, authenticated actor, acceptance time, and complete clause marker/hash; the consent audit table alone MAY retain that authenticated actor for local accountability, is governed by ACL and `AuditDays`, and never egresses. Only a current configuration version plus `privacy_acknowledgement_audit_id` that exactly references that row is acknowledged. The existing dashboard group is both administrator and operator; machine-account routes never receive provider configuration or investigation access.
- **Q: What evidence and result data are permitted? → A:** Evidence is a deterministic versioned allowlist DTO: stable source kind/ID facts first, then freshness/drain/status, local aggregates, and anonymous fleet aggregates, over source ±30 minutes clipped at snapshot, with deterministic omissions. It contains no canonical host/FQDN/domain/IP/customer identifier. Attempt labels are `source` and `peer_n`; known-channel codes and `custom_channel` replace arbitrary channel text. Evidence facts use `F001`–`F134`; evidence is at most 8,000 UTF-8 bytes and a request is at most 16 KiB. Only a fully validated bounded structured investigation report may persist.
- **Q: How do attempts start, retry, survive failure, and expire? → A:** An aggregate has immutable ordered attempts, not a mutable parent. At most 100 queued/running attempts exist globally, transactionally checked before evidence/attempt insertion: interactive roots at that cap return `429 queue_full` and automatic roots create no work. Separately, a source retains at most 100 attempts; a further interactive root/retry returns `409 attempt_limit_reached`. `started_at_ms` means worker/cancellation processing. `send_authorized_at_ms` is a durable marker committed immediately before `Client.Do`; it means a transmission MAY have begun, never proves provider receipt, and once non-null forbids automatic resend after uncertainty or restart. `send_completed_at_ms` means the local HTTP exchange returned. Retention never deletes running evidence while either the 30-second send lease or two-minute finalization lease is active; on lease expiry, recovery atomically terminalizes the row under the canonical restart/lease table before ordinary `AuditDays` deletion.
- **Q: How is a session drop determined and related to drains? → A:** In the same SQLite writer transaction that accepts `servers.last_result_json`, insert an idempotent `session_drop_observation_inbox` row with `accepted_sequence INTEGER PRIMARY KEY AUTOINCREMENT` and `UNIQUE(canonical_host, report_epoch_ms)`, containing accepted-at time, source-local offset/date, typed session presence/counts, and freshness, drain, and classification context. The detector drains strictly by `accepted_sequence`; `accepted_at_ms` is evidence/time only and MUST NOT determine ordering. It atomically consumes that durable inbox with its watermark, baseline, and source updates, then deletes or marks the row consumed; callback delivery only wakes the consumer. Startup drains pending inbox rows before accepting newer reports. Score existing `TotalSessions` (`Active + Disconnected`) exactly once per distinct, in-order, fresh accepted report; a successful numeric zero is valid, while nil/invalid/stale/out-of-order data is an unknown gap.

### Session 2026-09-27

- **Q: Should the legacy triage remain the investigation contract? → A:** No. Replace it with the fixed `openai_responses` OpenAI Responses API profile and a strict, bounded `anomaly_investigation_v1` reasoning report; deterministic detection, evidence boundaries, lifecycle, authorization, DPAPI, SQLite, retention, and no-remediation guarantees remain unchanged.

- **Q: How is dashboard authorization evaluated? → A:** Dashboard authorization uses the session’s existing login-time stored group snapshot, not a live directory-membership lookup. Before shared SSE subscription and periodically during it, the session must still exist and its stored snapshot must include the atomically current configured dashboard group. Changing `Dashboard.Group` invalidates all sessions and closes their streams, requiring reauthentication. External directory-membership changes take effect only on logout, session expiry, or reauthentication.

## Problem statements

1. Confirmed anomaly data can be distributed across telemetry, drain state, host freshness, and detector records, making a timely, reviewable investigation difficult.
2. Operators need a durable record of bounded evidence considered, an untrusted but structured reasoning report, and why an investigation did not run, without disclosing secrets or sensitive diagnostic content.
3. Sudden session-count losses are operationally important, but nil enumeration, stale telemetry, and report ordering must not be mistaken for zero sessions or an unexplained loss.
4. An optional external-provider integration must fail safely and visibly without altering deterministic detection, current evtspike behavior, or any operational control.

## User Scenarios & Testing

### User Story 1 — Investigate a confirmed anomaly with bounded evidence (Priority: P1)

An authenticated dashboard-group operator reviewing a confirmed evtspike event or eligible unexplained session drop can see an evidence-backed, untrusted reasoning report while retaining underlying deterministic facts.

**Why this priority**: It supplies operator value without delegating detection or remediation to a model.

**Independent Test**: Persist one confirmed spike and permitted retained context, enable acknowledged provider access and configure its protected credential, request an investigation as a dashboard-group operator, and inspect the durable validated report and provider-bound request capture.

**Acceptance Scenarios**:

1. **Given** a durable confirmed source with valid provider configuration, **when** automatic investigation is enabled or a dashboard-group operator requests investigation, **then** one attempt is created using only the allowlisted evidence DTO.
2. **Given** the same source is requested while its attempt is queued or running, **when** the duplicate request is accepted, **then** it returns the existing attempt ID and creates no concurrent provider call; a completed source creates no new attempt.
3. **Given** the provider returns a completed strict structured report, **when** the report is fully validated and displayed, **then** it presents overall assessment, evidence sufficiency, human-review state, bounded ranked hypotheses, missing evidence, and `recommended_diagnostic_checks` as untrusted guidance rather than conclusions or actions.
4. **Given** an attempt's evidence is produced, **when** its outbound DTO is inspected, **then** it contains no excluded identifier, free-form, raw diagnostic, secret, or arbitrary data category and uses deterministic fact IDs and omission markers.
5. **Given** provider access is disabled, **when** an anomaly is confirmed, **then** deterministic evtspike and session-drop behavior continue and no investigation request or external call is made.
6. **Given** a source already retaining 100 attempts, including attempts terminated locally for unavailable evidence, **when** any further root or linked retry is requested, **then** the transaction creates no attempt and returns `409 attempt_limit_reached`.
7. **Given** 100 queued or running attempts exist across distinct sources, **when** a manual or retry root is requested, **then** the pre-evidence transaction creates nothing and returns `429 queue_full`; **when** an automatic root is considered, **then** it creates zero work.

### User Story 2 — Review provenance and retry a failed or insufficient investigation (Priority: P1)

An authenticated dashboard-group operator can review a validated report, evidence summary, closed local provenance, and immutable lifecycle; distinguish unavailable, invalid, refused, incomplete, or insufficient evidence from a conclusion; and deliberately retry only a failed or insufficient attempt.

**Why this priority**: Trust requires a durable, transparent audit trail, especially when external analysis is unavailable or inconclusive.

**Independent Test**: Complete one investigation, induce one provider failure and one evidence-insufficient report, prove the 100-attempt per-source cap across roots/retries/local insufficiency, restart the service, and verify immutable history, interrupted-running behavior, expiry linearization, and authorized retry behavior.

**Acceptance Scenarios**:

1. **Given** a completed attempt, **when** an authenticated dashboard-group operator opens its history, **then** they see a stable source link, lifecycle timestamps/state, sanitized evidence summary, closed local provenance (`provider_profile=openai_responses`, `requested_model=gpt-6-astra`, RFC3339 `send_authorized_at`, `send_completed_at`, request byte counts, and validation outcome), immutable validated report or safe failure record, and retry lineage without excluded data, provider response text, IDs, returned model, usage, reasoning, headers, or provider metadata; source/list/detail views may resolve that link to the canonical host identity held by the deterministic source anomaly.
2. **Given** a report declares evidence insufficient or requires human review, **when** displayed, **then** the dashboard presents that state without presenting a hypothesis as a conclusion, recommendation, or automated action.
3. **Given** an attempt failed or has insufficient evidence, **when** an operator requests a retry and its deterministic source row still exists, **then** the system records one linked immutable attempt with a fresh bounded snapshot while preserving earlier attempts unchanged; if that source row has expired, it returns `404 source_not_found` after authorization and predecessor lookup and before evidence assembly, attempt creation, or provider work.
4. **Given** recovery finds a running attempt with an active applicable 30-second send lease or two-minute finalization lease, **when** recovery runs, **then** it preserves the row across restart and never automatically re-sends or reconstructs a result/provenance; **when** no applicable lease remains active, **then** recovery durably makes a row with `send_authorized_at_ms` null `failed/interrupted` and a row with that marker non-null and no terminal outcome `failed/storage_unavailable`.
5. **Given** a request lacks existing dashboard-group authorization, **when** it attempts detailed evidence, configuration, request, or retry access, **then** it is denied before evidence or attempt creation and no provider call is made.
6. **Given** an expired queued attempt or an invalid persisted available snapshot, **when** startup recovery/retention and worker startup run, **then** the expired queued row is pruned before any worker claim and makes zero egress, while the invalid snapshot is never claimed or egressed; a running row and its evidence are retained while either its active 30-second send lease or active two-minute finalization lease remains, and only after both expire does recovery atomically terminalize it under the canonical restart/lease table before a later ordinary retention pass may delete it.
7. **Given** a terminal SQLite write fails after a provider transmission, **when** the two-minute finalization lease is active in the same process, **then** exactly one bounded validated candidate may retry its SQLite write without resend and its running evidence is retention-protected; **when** that lease expires, **then** the candidate is discarded and, once SQLite is writable, the row atomically becomes `failed/storage_unavailable`, releases the worker, and may be normally retained or deleted; **when** the process restarts first, recovery preserves the running row while its applicable lease remains active, never retries SQLite finalization outside the original process, and terminalizes it only after that lease expires.

### User Story 3 — Identify a deterministic sudden session-count drop (Priority: P2)

An operator can review an independently determined lower-tail session-count anomaly through the same bounded investigation lifecycle, while planned drains and unknown context are distinguished from unexplained drops.

**Why this priority**: Sudden loss of sessions is a valuable anomaly source, but it must not weaken or redefine the mature evtspike contract.

**Independent Test**: Feed distinct, in-order reports through the baseline and confirmation sequence for an unexplained drop, drain-associated drop, stale report, out-of-order report, nil enumeration, and successful zero; separately train one host’s all-hours fallback and verify that reports from another host neither contribute to it nor make it ready, that 24-hour readiness spans `first_trained_at_ms` to eligible-normal-only `last_normal_trained_at_ms`, and that source detail projects persisted `confirmation_started_at_ms` and `confirmation_ended_at_ms` exactly; verify only the qualifying unexplained drop is provider-eligible.

**Acceptance Scenarios**:

1. **Given** fresh, valid, distinct, in-order reports and a mature lower-tail baseline, **when** `TotalSessions` falls below deterministic expectation and satisfies 2-of-3 confirmation, **then** the system creates a distinct unexplained session-drop anomaly eligible for investigation.
2. **Given** any non-`AllowAll` drain overlaps a confirmed drop or the confirmation horizon after that drain ends, **when** the drop is classified, **then** it is persisted as drain-associated and is not provider-eligible.
3. **Given** enumeration is nil, invalid, unavailable, stale, or out of order, **when** the detector evaluates it, **then** it records unknown, breaks confirmation, and neither trains a baseline nor creates a session-drop anomaly; a successful zero remains a valid numeric observation.
4. **Given** a candidate or confirmed drop, **when** baseline maintenance runs, **then** the candidate/confirmed value does not lower or train the baseline.
5. **Given** an existing upper-tail `SpikePayload` consumer, **when** session-drop detection is introduced, **then** evtspike semantics and contracts remain unchanged and the lower-tail anomaly has its own observable identity and additive dashboard API/SSE type, not a new notification trigger.
6. **Given** an accepted report is committed and the process crashes before its wake callback, **when** the service restarts, **then** startup drains its durable inbox row before accepting newer reports and applies its detector effects exactly once; no new agent wire field or report ID is required.
7. **Given** a session-drop source completes confirmation, **when** it is persisted and then returned by detail, **then** its central acceptance times are stored as `confirmation_started_at_ms` and `confirmation_ended_at_ms`, remain distinct from report-epoch fields, and are projected exactly.

### User Story 4 — Configure and diagnose a safe optional provider integration (Priority: P2)

A dashboard-group administrator/operator can explicitly configure acknowledged provider access and optional automatic investigation through session-only configuration APIs, observe safe operating state, and diagnose degradation without exposing credentials or causing operational actions.

**Why this priority**: The external integration must be deliberately enabled, observable, and harmless when unavailable.

**Independent Test**: Start with default configuration, store a valid protected credential, reject missing, unknown, false, or extra acknowledgement clauses, acknowledge and enable provider access with the exact closed acknowledgement object while automatic analysis remains off, then exercise invalid credentials, timeout, disablement, and configuration reload while observing safe GET and the ACL/AuditDays-governed local consent audit.

**Acceptance Scenarios**:

1. **Given** a default installation, **when** anomalies occur, **then** provider access and automatic investigation are disabled, no provider request is made, and deterministic detection is unaffected.
2. **Given** an administrator enables acknowledged provider access but leaves automatic investigation disabled, **when** a confirmed anomaly arrives, **then** no automatic investigation runs; an authorized operator may explicitly request one.
3. **Given** provider configuration is read or updated through a session-only API, **when** dashboard, logs, audit records, and telemetry are inspected, **then** only safe fields and `has_credential` are exposed; the DPAPI credential remains write-only with preserve, replace, and clear semantics.
4. **Given** the provider is unreachable, rejects credentials, returns a refusal, incomplete response, invalid structured output, exceeds a limit, or storage fails, **when** an attempt runs, **then** it has the required durable or structured local failure outcome, no partial report is asserted, and product detection, drains, notifications, and other functions continue.
5. **Given** automatic investigation is enabled and provider access is disabled or configuration becomes invalid, **when** current configuration takes effect or is revalidated before first send, **then** unsent work is cancelled, completed records remain readable, and no new provider call occurs until valid acknowledged configuration is restored.
6. **Given** a provider-settings PUT enables access, **when** its acknowledgement is not exactly the closed eight-clause all-true object, **then** enablement is rejected; **when** settings are retrieved, **then** the response exposes only `version` and `acknowledged`, never individual clause booleans.
7. **Given** provider access is enabled with a valid acknowledgement, **when** the service writes configuration, **then** it appends an immutable acknowledgement audit row before atomically recording its current version and audit ID; **when** the configuration write fails, **then** any unreferenced audit row is harmless and access remains unacknowledged.
8. **Given** a current `/api/v1/events` subscriber’s session expires, its stored login-time group snapshot lacks the atomically current configured dashboard group, or `Dashboard.Group` changes, **when** authorization is checked or configuration changes, **then** the stream closes and emits no subsequent investigation or session-drop event; a stale or non-group session is rejected with `403 access_denied` before subscription. Directory membership is not looked up live: an external membership change takes effect on logout, session expiry, or reauthentication.

## Edge Cases

- A durable evtspike event is replayed after restart or redelivered: its durable `event_spikes` ID plus denormalized source facts identifies the source and prevents a duplicate prospective automatic root attempt; canonical host identity remains on the source anomaly rather than being duplicated into the attempt's provider artifacts; no automatic backfill or replay occurs.
- A 2xx response that is not JSON is `response_invalid`. HTTP status alone maps non-2xx responses; their provider bodies and provider codes are not parsed. A 2xx response whose status is `failed` or whose error is non-null is `upstream_error`; its body/message is discarded. A successful `completed` envelope is accepted only when `incomplete_details` is present and JSON `null`; an absent, non-null, or wrong-typed value is `response_invalid`.
- A completed response with a refusal, incomplete status, missing structured output, absent/non-null/wrong-typed `incomplete_details`, invalid schema, invalid enum, out-of-bound field, unsupported character, forbidden canary or IP literal, or unknown/out-of-scope fact reference is not partially retained: raw response and associated provider data are discarded and the attempt records only the safe local outcome `provider_refused`, `response_incomplete`, or `response_invalid` as applicable.
- A provider response has headers over 16 KiB, decompressed body over 32 KiB, or an error body over 4 KiB: bounded data is discarded and the attempt fails safely without retaining raw content. `response_body_bytes` in provenance is the bounded decompressed JSON body byte count.
- When required permitted evidence is unavailable before send, the persisted local-insufficiency snapshot is host-free and exact: `snapshot_kind=unavailable`, `canonical_json={}`, SHA-256 of `{}`, and no fact rows. The attempt has `state=insufficient_evidence`, `terminal_reason=evidence_unavailable`, and no result or provenance. A provider-valid report declaring insufficient evidence has the same state, an empty terminal reason, and validated result and provenance. A valid egress snapshot instead has `snapshot_kind=available`, strict `EvidenceV1`, and fact rows.
- Evidence exceeds source ±30 minutes, snapshot clipping, evidence 8,000 UTF-8 bytes, or total request 16 KiB: field-order truncation is deterministic, records omission markers, and does not exceed the egress limit. `EvidenceV1` is built and canonicalized as an object; its canonical bytes are appended exactly once after `EVIDENCE_JSON_V1\n` in `input_text` and are escaped only by outer request JSON serialization.
- Configuration changes while queued: queued work may resume only after current configuration validation immediately before first send; disabling provider access or invalidating configuration terminalizes unsent work with no send timestamps, and a single request never mixes configuration.
- Pre-send SQLite failure: no egress occurs. A structured local diagnostic is emitted; an attempt failure becomes durable only if SQLite can write. Immediately before `Client.Do`, the service commits `send_authorized_at_ms` and its 30-second `send_lease_expires_at_ms`; it means a transmission MAY have begun and never proves provider receipt. After the local HTTP exchange returns, the process records `send_completed_at_ms`. If its terminal SQLite write then fails, it retains at most one bounded validated terminal outcome in memory through the fixed two-minute `finalization_lease_expires_at_ms`, discards the raw body immediately, emits a storage diagnostic, and retries the SQLite terminal write without another provider call. At lease expiry it discards that candidate; once SQLite is writable it atomically becomes `failed/storage_unavailable` and releases the worker.
- Startup/retention finds a queued attempt at or before the attempt-retention cutoff: it prunes that row before worker startup. A queued available snapshot whose persisted hash is invalid is never claimed or egressed. A claim requires `created_at_ms >= cutoff` and a valid snapshot/hash, so no expired queued attempt can egress. A running attempt and its evidence are retention-protected while either its active 30-second send lease or active two-minute finalization lease remains. When both leases expire, recovery atomically terminalizes it under the canonical restart/lease table before ordinary retention may delete the resulting terminal row.
- A baseline is scored or decayed after its last eligible normal training: that timestamp does not advance `last_normal_trained_at_ms`; all-hours readiness remains based on the span from `first_trained_at_ms` to eligible-normal-only `last_normal_trained_at_ms`. A session-drop confirmation persists central acceptance times independently of report epochs.
- A root, linked retry, or local-insufficiency creation would become the 101st retained attempt for its source: its transaction creates nothing and an interactive root/retry returns `409 attempt_limit_reached`. Independently, a manual, retry, or automatic root that would exceed 100 queued/running attempts globally checks that cap before evidence/attempt insertion; interactive requests return `429 queue_full` and automatic roots create no work. Session-drop detail therefore projects at most 100 immutable attempt summaries and uses only canonical terminal-reason enum values.

## Requirements

### Investigation lifecycle and provider boundary

- **FR-001**: The system MUST treat deterministic anomaly detection as independent from model investigation. A provider MUST NOT decide whether an anomaly occurred, alter detector baselines/confirmation, suppress a detector result, or initiate remediation.
- **FR-002**: The sole initial provider profile MUST be `openai_responses`, using direct `net/http` `POST` only to exactly `https://api.openai.com/v1/responses` over normal TLS 1.2+ trust. Production MUST use a dedicated `http.Transport` with `Proxy:nil` and MUST NOT use `ProxyFromEnvironment`; proxy credentials and proxy support are out of scope. The central dashboard/service instance alone MUST perform provider configuration, evidence assembly, calls, and persistence; no custom URL, redirect, userinfo, query, fragment, provider key, or provider call is permitted on an agent.
- **FR-003**: Provider access and automatic investigation MUST both be disabled by default and enabled separately. Enabling provider access requires a server-verifiable acknowledgement object with exactly these properties and no others: `version:"openai_responses_privacy_v1"`, `third_party_subprocessors:true`, `no_training_without_opt_in:true`, `default_abuse_monitoring_up_to_30_days:true`, `store_false_application_state_only:true`, `temporary_prompt_cache_possible:true`, `zdr_mam_separate_approval:true`, `audit_days_local_only:true`, and `global_endpoint_no_regional_guarantee:true`. A missing, unknown, wrong-version, non-boolean, or false clause/value MUST reject enablement. The authoritative acknowledgement audit is append-only SQLite table `investigation_privacy_acknowledgements` with `id`, fixed `version`, authenticated `actor`, `accepted_at_ms`, and `clause_set_hash` (or a fixed complete-clause marker). The service MUST validate every clause, append the immutable audit row first, then atomically write configuration containing the current acknowledgement version and `privacy_acknowledgement_audit_id` referencing that row; a configuration-write failure MAY leave only an unreferenced harmless audit row. Access is acknowledged only when the configured current version and referenced audit ID exactly match an audit row with the complete clause set; any other condition fails closed. Settings GET exposes only safe `version` and `acknowledged`, never clauses, actor, audit ID, or timestamps.
- **FR-004**: Existing dashboard sessions MUST authorize administrator/operator UI APIs using their login-time stored group snapshot, not a live directory-membership lookup. An authorized session’s snapshot MUST include the atomically current configured dashboard group. Machine-account routes MUST receive neither provider configuration nor investigation access. Authorized operators MAY request an eligible durable anomaly and retry only a failed or insufficient attempt; unauthorized work MUST stop before evidence or attempt creation. A `Dashboard.Group` change MUST invalidate all sessions and require reauthentication; external directory-membership changes take effect only on logout, session expiry, or reauthentication.
- **FR-005**: The system MUST consume durable confirmed evtspike events idempotently using durable `event_spikes` identity plus denormalized source facts. It MUST NOT change existing evtspike detection, notification, payload semantics, or consumers.
- **FR-006**: A source aggregate MUST expose immutable ordered attempts, not a mutable parent lifecycle. Attempt state MUST progress only `queued` → `running` → `completed`, `insufficient_evidence`, or `failed`; `completed_at_ms` MUST be null only for `queued` and `running`, and non-null for every terminal state. `started_at_ms` means worker or cancellation processing began, not provider egress. Every attempt has nullable `send_authorized_at_ms` and `send_completed_at_ms`. In a durable transaction immediately before `Client.Do`, the worker MUST set `send_authorized_at_ms`; this is a possible-send marker that means a transmission MAY have begun, never proves provider receipt, and permanently forbids automatic resend after uncertainty or restart. `send_completed_at_ms` means the local HTTP exchange returned, not provider receipt. Local insufficiency, invalid/currently disabled configuration cancellation, request-limit termination, or any other pre-send terminal MUST retain null send timestamps. Closed SQLite/provider provenance MUST use `send_authorized_at_ms` and `send_completed_at_ms`, with no request-started/request-completed aliases. Dashboard REST projections and their OpenAPI/task contracts MUST use RFC3339 `created_at`, `started_at`, `send_authorized_at`, `send_completed_at`, and `completed_at`, never `_ms` names; SQLite/internal fields retain their `_ms` names.
- **FR-007**: A successful provider result MUST be a fully validated strict JSON object from a `completed` Responses status whose `incomplete_details` property is present and JSON `null`, conforming to the `anomaly_investigation_v1` schema supplied through `text.format` with `strict:true`. An absent, non-null, or wrong-typed `incomplete_details` is `response_invalid`. The schema MUST set `additionalProperties:false` at every object level and require every declared property: `result_version`; bounded `summary` with valid fact IDs; `overall_assessment` enum; `evidence_sufficiency` enum; `human_review_required` boolean; zero-to-five sequentially ranked `hypotheses` with bounded statement, confidence, and supporting/contradicting fact-ID lists; zero-to-six bounded `missing_evidence` items; and one-to-six bounded read-only `recommended_diagnostic_checks` with `check_type`, hypothesis, and fact references. Every report prose field MUST have the strict schema pattern and local validation `^(?:[\x21-\x2E\x30-\x3B\x3D\x3F\x41-\x5B\x5D-\x5F\x61-\x7E]|[\x21-\x2E\x30-\x3B\x3D\x3F\x41-\x5B\x5D-\x5F\x61-\x7E][\x20\x21-\x2E\x30-\x3B\x3D\x3F\x41-\x5B\x5D-\x5F\x61-\x7E]*[\x21-\x2E\x30-\x3B\x3D\x3F\x41-\x5B\x5D-\x5F\x61-\x7E])$`: trimmed printable ASCII, ordinary ASCII spaces only, existing field byte limits, and no `/`, `\`, `<`, `>`, `@`, or backtick. The strict schema and local validator MUST both reject IPv4/IPv6 literals and case-insensitive ASCII-normalized substring containment of every configured sensitive canary. This is a bounded canary/format check, not a claim to detect every invented hostname or domain absent from evidence/canaries. The developer prompt MUST request read-only checks; `check_type` constrains intent; no semantic classifier is claimed to prove prose free of commands or remediation. The response is untrusted guidance; hypotheses and recommended diagnostic checks MUST NOT be presented as conclusions or actions.
- **FR-008**: The product MUST NOT autonomously run commands, PowerShell, tools, configuration changes, drains, restarts, notifications, or any remediation because of investigation evidence or provider output. Recommended diagnostic checks MAY be displayed only as bounded read-only operator guidance, MUST be labelled untrusted, and MUST NOT be executed, routed to tools, or interpreted as authorization for action.

### Evidence protection, storage, and retention

- **FR-009**: Before egress, the central service MUST build `EvidenceV1` as a versioned allowlist object field by field in this order: stable source kind/ID facts; freshness, drain, and detector status; local aggregates; anonymous fleet aggregates. It MUST assign deterministic fact IDs only from `F001` through `F134`; its source window MUST be ±30 minutes clipped at evidence snapshot; evidence MUST be at most 8,000 UTF-8 bytes. Attempt labels MUST be `source` and `peer_n`; channels MUST use known-channel codes or `custom_channel`; omissions MUST be deterministic. A sendable snapshot MUST be `snapshot_kind=available` with strict `EvidenceV1` and fact rows. The canonical bytes of that object MUST be appended once after literal `EVIDENCE_JSON_V1\n` in `input_text`; the outer request JSON serializer alone escapes those bytes.
- **FR-010**: Investigation evidence, results, attempts, provenance, and diagnostics MUST exclude source, customer, user, and session identities; canonical host/FQDN/domain/IP/customer identifiers; usernames; `changed_by`; free text; arbitrary or nonfixed URLs; paths; generic maps; raw structs; Event Log messages/XML; dumps; credentials; notification secrets; and arbitrary files. A fully validated investigation result MAY contain only the bounded model-generated prose fields defined by `anomaly_investigation_v1`; those fields MUST meet FR-007 format, canary, literal-IP, and fact-reference validation. The sole exceptions are that `investigation_privacy_acknowledgements` MAY retain its authenticated actor for local accountability, subject to ACL and `AuditDays` and never egressed, and closed local provenance MAY retain only the fixed literal `https://api.openai.com/v1/responses` as a local constant. Canonical host identity MUST remain on the durable deterministic source anomaly and MAY be returned only by authorized source/list/detail REST projections. SSE investigation payloads MUST be source-ID-only and host-free. This restriction MUST NOT remove or alter existing authenticated source/list/detail host identity behavior.
- **FR-011**: Requests MUST use `Authorization: Bearer <credential>`, with the existing DPAPI write-only `config.json` credential semantics. The OpenAI key MUST remain encrypted in long-lived configuration. Only `internal/investigation` MAY expose a narrow decrypt-for-send accessor; plaintext MUST NOT reside in Config, ServiceConfig, DashboardConfig, RemoteSettings, closures, or worker state, and temporary key bytes MUST be zeroed and released after request construction. The credential MUST NOT be returned by APIs, logged, telemetered, persisted as evidence/audit data, or treated as request-body evidence.
- **FR-012**: Sanitized evidence, investigation lifecycle, immutable results, provenance, and attempt retention MUST be stored in existing SQLite. Attempt retention MUST be independently anchored to attempt `created_at_ms` and bounded by `AuditDays`, without changing evtspike source retention. Retention MUST delete expired queued and terminal attempts, but MUST NOT delete a running attempt or its evidence while either its active bounded 30-second send lease or active bounded two-minute finalization lease remains. Once both leases expire, recovery MUST atomically terminalize the running row according to the canonical restart/lease table before ordinary `AuditDays` deletion: `send_authorized_at_ms IS NULL` becomes `failed/interrupted`; non-null `send_authorized_at_ms` with no durable terminal outcome becomes `failed/storage_unavailable`. Recovery MUST NOT reconstruct result/provenance or resend either row. Session-drop source rows MUST be independently deleted in chunks where `detected_at < now - AuditDays`; permanent host removal MUST also delete that host’s pending session-drop inbox rows.
- **FR-013**: The pre-send transaction MUST, before inserting evidence or an attempt, transactionally count queued plus running attempts globally across all sources. The global maximum is 100: an interactive manual or retry root at the limit MUST return `429 queue_full` and create nothing; an automatic root at the limit MUST create zero work. The distinct per-source retained-attempt maximum remains 100 and MUST be checked transactionally for every root, linked retry, and local-insufficiency attempt; an interactive further root or retry returns `409 attempt_limit_reached` and creates nothing. If the pre-send transaction fails, the system MUST make zero egress and emit a structured local diagnostic; it MUST record a durable failure only when SQLite can write. A worker claim transaction MUST require `created_at_ms >= now - AuditDays` and a valid persisted sendable snapshot with its matching hash; otherwise it MUST not claim or egress the row. Immediately before `Client.Do`, a separate durable transaction MUST set `send_authorized_at_ms` and its 30-second `send_lease_expires_at_ms`. After that marker is non-null no automatic resend is permitted, including after transport uncertainty, finalization failure, or restart. When the local HTTP exchange returns, the attempt records `send_completed_at_ms` and begins its exactly two-minute in-process finalization lease. If its terminal SQLite write fails, raw provider material MUST be discarded immediately and exactly one bounded, fully validated terminal candidate MAY be held only in process memory and retried to SQLite without resend while that finalization lease is active. Retention MUST protect the running attempt and its evidence while either its send lease or finalization lease is active. After both expire the candidate MUST be discarded and recovery MUST atomically terminalize the row under the canonical restart/lease table before ordinary retention deletion; a non-null `send_authorized_at_ms` becomes `failed` with `terminal_reason=storage_unavailable`, while a null marker becomes `failed` with `terminal_reason=interrupted`.
- **FR-014**: Authenticated dashboard-group operator views MUST distinguish observed evidence, deterministic anomaly facts, untrusted provider guidance, omitted categories, failure/insufficiency states, and unavailable pre-upgrade context. Source/list/detail REST views MAY show the canonical host identity held by the deterministic source anomaly, but evidence, result, provenance, and provider diagnostics MUST remain sanitized. Validated provider prose MUST be HTML-escaped plain text, never rendered as Markdown or HTML. Adjacent labels MUST be exactly `Untrusted model hypothesis` and `Untrusted model-suggested diagnostic check`.
- **FR-015**: Every request MUST be foreground, non-streaming, and stateless, with `model:"gpt-6-astra"`, `store:false`, `background:false`, `stream:false`, `truncation:"disabled"`, `reasoning.effort:"high"`, `max_output_tokens:8192`, and strict `text.format` for `anomaly_investigation_v1`. Requests MUST include no tools, functions, web/files/MCP/code/computer/shell capabilities, conversations, previous-response reference, polling, or reasoning summaries. Total request size MUST be at most 16 KiB; request/response headers MUST be at most 16 KiB, decompressed response bodies at most 32 KiB, and discarded error bodies at most 4 KiB. `response_body_bytes` MUST count decompressed bounded JSON body bytes. The service MUST discard raw response content, refusal/error text, response IDs, returned model, usage, reasoning, headers, and all other provider metadata.

### Session-drop anomaly detection

- **FR-016**: The central service MUST add a separately testable lower-tail detector that scores existing `TotalSessions` (`Active + Disconnected`) exactly once per distinct, in-order, fresh accepted report and preserves a distinct representation from the existing upper-tail evtspike `SpikePayload` contract. In the same SQLite writer transaction that persists accepted `servers.last_result_json`, it MUST insert an idempotent `session_drop_observation_inbox` row with `accepted_sequence INTEGER PRIMARY KEY AUTOINCREMENT` and `UNIQUE(canonical_host, report_epoch_ms)`. That row MUST contain `accepted_at_ms`, source-local offset/date, typed session-presence and count fields, and the freshness, drain, and classification context used by detection. `accepted_sequence` is the private global acceptance order; the detector MUST drain pending rows strictly by it, and `accepted_at_ms` is evidence/time only and MUST NOT order consumption. The report callback MUST only wake the consumer. The detector MUST atomically consume each inbox row together with its per-host watermark, baseline/source updates, and any resulting anomaly, then delete or durably mark the row consumed. Startup MUST drain pending inbox rows before accepting newer reports. No new agent wire field or report ID is permitted.
- **FR-017**: A successful numeric zero MUST be a valid observation. Nil enumeration, invalid/unavailable/stale telemetry, and out-of-order reports MUST be unknown gaps that break confirmation, do not train, and are never persisted or aggregated as numeric zero.
- **FR-018**: For each host, the detector MUST preserve 96 local-time slots and one all-hours fallback trained only from that host’s eligible normal observations; it MUST NOT pool session counts across hosts. A slot MUST be ready only after seven distinct eligible local days. Each baseline MUST persist `first_trained_at_ms` and `last_normal_trained_at_ms`; the latter MUST update only on eligible normal training, never on score, decay, candidate, confirmed-drop, drain-associated, or unknown observations. The all-hours fallback MUST be ready only after at least 20 eligible normal observations spanning at least 24 hours from `first_trained_at_ms` to `last_normal_trained_at_ms`, never from a decay or score timestamp. The detector MUST preserve time-based decay, default lower predictive-tail threshold `1e-4`, default minimum drop of 3 sessions and 30% from last eligible observation, fixed 2-of-3 consecutive confirmation, and default 60-minute per-host cooldown. These limits MUST be validated configuration.
- **FR-019**: Candidate and confirmed drops, any non-`AllowAll` drain overlap, and one confirmation horizon after drain end MUST neither lower nor train the baseline. Confirmed drops MUST persist central acceptance times `confirmation_started_at_ms` and `confirmation_ended_at_ms`, distinct from any report-epoch fields; detail MUST project both values exactly. Confirmed drops MUST be persisted with their canonical registered-host identity as `unexplained`, `drain_associated`, or `unknown_context`; only `unexplained` is provider-eligible.
- **FR-020**: An unexplained confirmed session-drop anomaly MUST use the same durable, opt-in investigation lifecycle as evtspike. It MUST add distinct authenticated dashboard-group source/list/detail REST API types that can identify the affected registered host, and host-free investigation SSE types using exactly one literal `data:` line containing the existing JSON envelope `{type,host?,data,timestamp}` with no named `event:` line. Investigation SSE payloads MUST omit the optional `host` member and identify sources only by kind/ID. It MUST NOT add a notification trigger. The detector MUST function when investigation is disabled or unavailable.

### Configuration, observability, compatibility, and degraded operation

- **FR-021**: Session-only configuration APIs MUST expose only safe provider fields and `has_credential`. Every provider-settings `PUT` MUST include an explicit credential command of `preserve`, `replace`, or `clear`; omission is invalid and `preserve` is never implicit. Credentials MUST retain existing DPAPI write-only semantics. Unknown provider configuration fields MUST round-trip only where supported; an older version that rewrites configuration MAY drop them.
- **FR-022**: The diagnostic surface MUST expose disabled, configured/ready, automatically enabled, degraded, or failing provider states; attempt counts; and safe failure reasons, without credentials, raw evidence, excluded data, provider response text, IDs, usage, reasoning, headers, or provider metadata.
- **FR-023**: The system MUST use one worker, a global maximum of 100 queued plus running attempts across all sources, 10 requests/minute with burst 2, and a 30-second request timeout. The global cap MUST be checked transactionally before evidence or attempt insertion for manual, retry, and automatic roots; interactive calls at the cap return `429` with error code `queue_full`, while automatic roots create zero work. Each source MUST retain at most 100 attempts in total, transactionally enforced before every root, linked retry, and local-insufficiency creation; a further interactive root or retry MUST return `409` with error code `attempt_limit_reached` and create nothing. Each attempt MUST make at most one wire transmission: the durable `send_authorized_at_ms` marker and bounded 30-second send lease are committed immediately before `Client.Do`, the marker means transmission MAY have begun rather than provider receipt, and it forbids automatic resend once non-null. `send_completed_at_ms` records only that the local HTTP exchange returned. The two-minute finalization lease applies only to the same-process retry of one bounded validated terminal SQLite write and never authorizes resend.
- **FR-024**: Immediately before first send, the worker MUST validate current configuration. Queued rows MAY resume only after that validation and the retention-valid claim transaction; provider disablement or invalid configuration MUST terminalize unsent work without send timestamps. On startup and periodically, recovery MUST preserve every durable running row with an active applicable bounded send or finalization lease. Only after no applicable lease remains active, recovery MUST terminalize every durable running row lacking a durable terminal outcome according to the canonical restart/lease table: null `send_authorized_at_ms` becomes `failed/interrupted`; non-null becomes `failed/storage_unavailable`. It MUST NOT automatically re-send or reconstruct a lost result/provenance. No expired queued attempt MAY egress.
- **FR-025**: Provider unavailability, authentication failure, refusal, incomplete or invalid response, bounded-request failure, timeout, or storage failure MUST NOT prevent anomaly detection, evtspike notifications, drain operations, freshness evaluation, or normal dashboard use.
- **FR-026**: Existing dashboard consumers and evtspike clients that do not recognize investigation/session-drop additions MUST continue to function. Additions MUST NOT require existing `SpikePayload` consumers to interpret a lower-tail anomaly.
- **FR-027**: Upgrade and rollback MUST preserve pre-existing known configuration/data, audit, telemetry, and source records. An older version MAY ignore new investigation records and MAY drop unknown provider fields if it rewrites configuration, but a rollback or rewrite that clears, drops, or invalidates `privacy_acknowledgement_version` or `privacy_acknowledgement_audit_id` MUST fail closed. After re-upgrade, provider access MUST remain disabled until configuration atomically references a new matching immutable acknowledgement audit row; no global historical freshness/status data is added to backfill evidence.
- **FR-028**: Session-drop list/detail contracts MUST use decimal-string IDs and cursors. List `before`, when present, MUST be a decimal cursor; invalid/malformed query values return the documented validation error; a closed list object returns items and `next_before`, which is null on exhaustion. List items MUST NOT include attempt summaries. Detail returns a closed object including `baseline_model_version` and the complete retained immutable attempt-summary projection. Both endpoints use the common dashboard auth/error contract exactly: an expired or missing session returns `401` with `{"error":{"code":"session_expired"}}`; an authenticated caller without dashboard-group access returns `403` with `{"error":{"code":"access_denied"}}`. Every route error, including validation and not-found errors, MUST use the body shape `{"error":{"code":"..."}}`. They MUST define not-found and validation errors and specify nullability for every nullable property. Only authorized source/list/detail REST projections may resolve host identity.
- **FR-029**: A session-drop detail's complete retained immutable attempt-summary projection MUST contain no more than the source’s 100 retained attempts. Its `terminal_reason` MUST use exactly the canonical attempt terminal-reason enum defined by the persisted data model/provider contract; stale aliases, translated synonyms, and ad hoc detail-only values are forbidden.
- **FR-030**: Implementation/review checklists MAY require intentional platform, API, and security bindings that are necessary to enforce this specification. They MUST reject incidental implementation detail rather than treating every binding as forbidden.
- **FR-031**: The shared `/api/v1/events` SSE endpoint MUST authorize the caller before subscription, while preserving compatibility for existing authorized event consumers. Authorization MUST require that the session exists and its login-time stored group snapshot includes the atomically current configured dashboard group; it MUST NOT perform a live directory-membership lookup. The endpoint MUST periodically revalidate those two conditions for every subscription and promptly close a stream that fails either, emitting no further events. A stale or non-group session MUST receive `403 access_denied` before subscription. A `Dashboard.Group` configuration change MUST atomically invalidate all sessions and close all streams, requiring reauthentication. External directory-membership changes take effect only on logout, session expiry, or reauthentication.

### Key Entities

- **Investigation Source Aggregate**: An immutable stable-kind/ID link to a deterministic evtspike source—its durable `event_spikes` ID plus denormalized source facts—or to a distinct deterministic session-drop source; the linked durable deterministic source anomaly, not the aggregate or its attempts, retains canonical host identity. It exposes ordered immutable attempts without a mutable parent lifecycle.
- **Sanitized Evidence Snapshot**: A host-free snapshot that is either `snapshot_kind=available` with strict bounded `EvidenceV1`, deterministic `F001`–`F134` facts, ordered stable source kind/ID facts through anonymous fleet aggregates, and canonical bytes appended once to `input_text`; or the exact local-insufficiency shape `snapshot_kind=unavailable`, `canonical_json={}`, SHA-256 of `{}`, and no fact rows. Neither shape contains canonical host/FQDN/domain/IP/customer identity.
- **Investigation Attempt**: A durable `queued`, `running`, `completed`, `insufficient_evidence`, or `failed` attempt linked to a source only by stable kind/ID and optional retry predecessor. It records worker/cancellation `started_at_ms`, nullable `send_authorized_at_ms` and `send_completed_at_ms`, and bounded `send_lease_expires_at_ms` and `finalization_lease_expires_at_ms`. The authorization marker and 30-second send lease are committed immediately before `Client.Do`; the marker proves only that transmission MAY have begun, not provider receipt, and prevents automatic resend once non-null. A source retains no more than 100 attempts, while all sources share at most 100 queued/running attempts. `completed_at_ms` is null only while queued/running and non-null when terminal. `terminal_reason`, including a session-drop detail summary, is exactly a member of the canonical persisted attempt terminal-reason enum, with no stale aliases. REST projections use RFC3339 `created_at`, `started_at`, `send_authorized_at`, `send_completed_at`, and `completed_at`; internal SQLite fields retain `_ms`.
- **Session-Drop Observation Inbox**: A durable idempotent row with `accepted_sequence INTEGER PRIMARY KEY AUTOINCREMENT` and `UNIQUE(canonical_host, report_epoch_ms)`, inserted in the same writer transaction as accepted `servers.last_result_json`. It records `accepted_at_ms`, source-local offset/date, typed session presence/counts, and freshness, drain, and classification context. `accepted_sequence` is the private global acceptance order and is the sole drain order; `accepted_at_ms` is evidence/time only. The detector consumes rows strictly by `accepted_sequence`, atomically with watermark, baseline, and source updates, and deletes or marks them consumed; callbacks only wake the consumer. Startup drains pending rows before newer reports, and permanent host removal deletes pending rows for that host.
- **Investigation Result**: An immutable, fully validated `anomaly_investigation_v1` report: result version, bounded fact-ID summary, assessment and evidence state, human-review flag, ranked hypotheses, missing evidence, and `recommended_diagnostic_checks`. It is untrusted operator guidance, contains no raw provider material or source/customer/user/session identity, and cannot trigger execution or remediation.
- **Provider Provenance**: Closed local provenance only for provider-validated results: `provider_profile=openai_responses`, `requested_model=gpt-6-astra`, `send_authorized_at_ms`, `send_completed_at_ms`, request byte counts including decompressed JSON `response_body_bytes`, validation outcome, and only the fixed literal `https://api.openai.com/v1/responses` as a local endpoint constant. It excludes source/customer/user/session identities; arbitrary or nonfixed URLs; raw response/refusal/error text; response IDs; returned model; usage; reasoning; headers; and provider metadata.

- **Session-Drop Anomaly**: A distinct deterministic lower-tail condition with the canonical registered-host identity, source facts, baseline/confirmation context, persisted central `confirmation_started_at_ms` and `confirmation_ended_at_ms` acceptance times distinct from report-epoch fields, `baseline_model_version`, freshness state, and one of `unexplained`, `drain_associated`, or `unknown_context`. Detail projects both central acceptance times exactly.

| Failure | Required behavior |
|---|---|
| Provider access or automatic investigation disabled | Make no automatic external request; explicit request is available only to authorized dashboard-group operators when acknowledged provider access is configured. Disabling access cancels unsent work. |
| Unauthorized UI or machine-account route | Deny before evidence/attempt creation; disclose no provider configuration or investigation data and make no provider call. |
| Provider endpoint, method, transport, or request contract differs from `openai_responses` | Reject configuration/request locally; make no external request. Production transport has `Proxy:nil` and never uses `ProxyFromEnvironment`. |
| Provider unreachable, timeout, rate limit, or upstream/network failure | Persist terminal failed attempt when SQLite can write; make no autonomous HTTP retry; preserve all detector/dashboard operation. |
| Provider credentials rejected | Persist safe authentication failure without logging/returning credential; show degraded configuration. |
| Completed response is refused | Discard provider content and record terminal `provider_refused` outcome without partial report or provider provenance. |
| Completed response is incomplete | Discard provider content and record terminal `response_incomplete` outcome without partial report or provider provenance. |
| A completed response omits `incomplete_details`, supplies it as non-null, or supplies a wrong type | Discard provider content and record terminal `response_invalid` without partial report or provider provenance. |
| A 2xx response is non-JSON, malformed, oversized, unexpected tool output, missing structured output, or fails schema/prose/fact-reference validation | Discard provider content and record terminal `response_invalid` outcome without partial report or provider provenance. |
| A 2xx response has `status=failed` or non-null error, or any non-2xx HTTP status occurs | Discard body/message; map the former to terminal `upstream_error` and the latter by HTTP status alone without parsing provider bodies/codes. |
| SQLite terminal write fails after a request is sent | Do not resend. Record `send_completed_at_ms` after the local HTTP exchange returns, discard raw body immediately, retain only one bounded validated terminal outcome in process memory through the fixed two-minute finalization lease, and retry its SQLite write only in that same process. Retention protects the running row and evidence while either the active 30-second send lease or active two-minute finalization lease remains. After both expire, discard the candidate and atomically terminalize under the canonical restart/lease table; once SQLite is writable it becomes `failed/storage_unavailable` and releases the worker. On restart, preserve the running row while its applicable lease remains active; never reconstruct its result/provenance or retry finalization outside the original process, and terminalize it only after no applicable lease remains active. |
| Required retained evidence is unavailable before send while its source row still exists | Persist the host-free unavailable snapshot (`snapshot_kind=unavailable`, `canonical_json={}`, SHA-256 of `{}`, no fact rows), `state=insufficient_evidence`, `terminal_reason=evidence_unavailable`, no result, and no provenance when possible; never retrieve arbitrary files or unbounded history. |
| Provider-valid report declares insufficient evidence | Persist `state=insufficient_evidence` with empty terminal reason plus validated result and provenance; REST/SSE projections distinguish it from local `evidence_unavailable` insufficiency without exposing host identity in investigation SSE. |
| Source missing or expired for an operator request or retry | After authorization and predecessor lookup, return `404 source_not_found` before evidence assembly, attempt creation, or provider work; do not reuse stale evidence or fabricate placeholder facts. |
| Duplicate source request/delivery | Queued/running duplicate returns existing ID; completed source creates nothing; only failed/insufficient source may create a linked retry. |
| Global queued/running cap reached | Before evidence or attempt insertion, manual/retry roots return `429 queue_full` and create nothing; automatic roots create zero work. |
| Source has 100 retained attempts | Transaction creates no root, retry, or local-insufficiency attempt beyond the cap; a further interactive root/retry returns `409 attempt_limit_reached`. |
| Queued attempt is expired or lacks a valid persisted sendable snapshot/hash | Startup retention removes expired queued work before worker start; claim rejects either condition and makes zero egress. |
| Attempt crosses retention cutoff while running | Retention protects the row and evidence while either its active 30-second send lease or active two-minute finalization lease remains. After both expire, recovery atomically terminalizes it under the canonical restart/lease table, after which a later ordinary retention pass may delete the terminal row. |
| Running work at crash/restart | Never automatically re-send or reconstruct a validated outcome, result, or provenance. Startup and periodic recovery preserve the running row while its applicable bounded send or finalization lease remains active. Only after no applicable lease remains active does a row with `send_authorized_at_ms IS NULL` become `failed/interrupted`, or a row with non-null `send_authorized_at_ms` and no durable terminal outcome become `failed/storage_unavailable`. |
| Session enumeration/freshness/order unknown | Record unknown, not zero; break confirmation; do not train or create unexplained session-drop anomaly. |
| Drain overlaps drop or post-drain horizon | Persist `drain_associated`; do not train/lower baseline or make provider eligible. |
| Permanent host removal | Delete the host’s baseline/detector state and all pending `session_drop_observation_inbox` rows for that host. |
| Session-drop source retention boundary reached | Delete session-drop source rows independently in chunks where `detected_at < now - AuditDays`; baseline/detector state remains until permanent host removal. |

## Assumptions and explicit non-goals

- OpenAI Responses at the fixed `openai_responses` endpoint accepts bounded structured evidence and can return the required strict structured report. Its output may be unavailable, refused, incomplete, invalid, or insufficient and is never authoritative.
- The existing dashboard group supplies both administrator and operator authorization for this specification; machine accounts are excluded from provider configuration and investigation access.
- `AuditDays` is authoritative only for local investigation copies. DrainCtl cannot enforce OpenAI or subprocessor retention/deletion, ZDR/MAM eligibility, prompt-cache processing, training opt-in choices, or regional processing at the fixed global endpoint.
- Existing telemetry retains aggregate, non-sensitive context needed for permitted evidence. Its existing operational telemetry, audit, and dashboard host-identity behavior remains unchanged. Missing retained or pre-upgrade context remains unavailable rather than being reconstructed from unbounded sources or new global history.
- This feature does not change evtspike detector semantics, `SpikePayload`, notification rules, channel subscriptions, or baseline behavior.
- This feature does not put provider credentials/calls on agents, add a notification trigger for session drops, add autonomous remediation, incident closure, commands, PowerShell execution, tools, configuration changes, drains, restarts, notifications, or provider-driven human-action recommendations. Bounded validated report prose and recommended diagnostic checks are allowed only as untrusted operator guidance and are never executed or routed to tools.
- This feature does not send raw event data, per-session data, canonical host/FQDN/domain/IP/customer identifiers, free text, URLs/paths, generic/raw structures, dumps, arbitrary files, credentials, notification secrets, or customer URLs as evidence to a provider; it retains canonical host identity only on durable deterministic source anomalies and exposes it only through authenticated dashboard-group source/list/detail APIs, never browser-local durable state.
- This feature does not create a general-purpose chat interface, browser-local investigation store, provider fallback that changes egress, model-driven anomaly detector, automatic backfill/replay, global historical freshness/status store for backfilled evidence, tools/functions, web/files/MCP/code/computer/shell access, conversations, previous-response reuse, polling, or reasoning-summary retention.
