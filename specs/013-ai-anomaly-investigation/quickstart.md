# Implementation Validation Quickstart: AI Anomaly Investigation (013)

Use this runbook on an isolated Windows dashboard/service installation with a disposable SQLite database and synthetic reports. It validates [spec.md](./spec.md); it is not authorization to disclose production data to OpenAI. Synthetic response scenarios use an injected fake and make **no real OpenAI call**; the separate proxy-isolation scenario uses the actual production transport but injects its dial boundary to prevent external I/O.

## Safety and fixture rules

- Use a recording injected `http.RoundTripper`/`http.Client` only for synthetic response scenarios. It must preserve the requested URL but never dial, redact the Bearer value, count requests and redirect attempts, measure headers/body, retain only a transient test-local request inspection, and return selectable synthetic Responses envelopes, transport errors, delays, and bounded headers/bodies. Delete its capture after each scenario.
- Synthetic response scenarios must not configure an endpoint override, proxy, local server, redirect, TLS bypass, or real provider key. Their captured target must always be `POST https://api.openai.com/v1/responses`. The dedicated proxy-isolation scenario is the sole exception for hostile local proxy listeners.
- Use synthetic source IDs, aggregate metrics, and excluded-data canaries. A synthetic registered-host canary may exist only on the deterministic source row and the authorized deterministic source/list/detail REST projection; it must never enter evidence, attempts, reports, provenance, captures retained as results, SSE, or browser durable state. Investigation SSE payloads are source-ID-only.
- Privacy exceptions are narrow and local: `investigation_privacy_acknowledgements` alone may retain its authenticated actor for local accountability, governed by ACL and `AuditDays`; closed provenance alone may retain the fixed literal `https://api.openai.com/v1/responses` as a local constant. Neither exception may egress. Source/customer/user/session identities and arbitrary or nonfixed URLs remain forbidden in all investigation evidence, results, attempts, provenance, diagnostics, captures, REST/SSE, and test records.
- Treat all provider report prose as untrusted data. The fixture must prove it is rendered as text and is never executed, interpreted as a command, routed to a tool/remediation path, or used to change configuration; it must not claim semantic classification can prove prose has no command/remediation meaning.
- Run dashboard-group, non-dashboard, and machine-account requests under separate synthetic identities. Do not broaden authorization to make a test pass.
- Use supported routes and normal service lifecycle. Do not edit `config.json`, DPAPI data, or SQLite rows directly, except to create the explicit old-schema/old-version acknowledgement migration fixture or a controlled storage fault fixture.
- Record only state, IDs, counts, hashes, redacted assertions, and safe reason enums. Never retain a request body, Bearer value, DPAPI ciphertext, raw response/error/refusal text, response ID, returned model, usage, reasoning, or database copy in test evidence. The acknowledgement audit's authenticated actor and the closed-provenance fixed endpoint literal are the only allowed local test observations of the two privacy exceptions.

**Cleanup after every section:** disable provider access and automatic investigation through the dedicated settings route; clear the synthetic credential with explicit `clear`; discard fake-response and production-dial captures; restore normal test configuration and proxy environment; and remove disposable data only after required migration/rollback observations.

## 1. Prerequisites and baseline

1. Build/install the Windows dashboard/service under test with fresh disposable configuration and SQLite data. Create dashboard-group, non-dashboard, and machine-account test identities.
2. Prepare one confirmed `event_spikes` source and deterministic accepted reports for two synthetic registered hosts. Canonical host identity remains only in deterministic source rows; investigations link by `source_kind` and `source_id`.
3. Run synthetic response scenarios with the non-dialing recording fake. It must assert the exact fixed Responses URL, request method, headers, byte limits, redirects, and forbidden-canary absence; it may return only synthetic bounded payloads.
4. Separately construct the provider client through its actual production wiring so it owns the actual production `http.Transport`; do not replace its `RoundTripper`. Start hostile local HTTP and HTTPS proxy listeners that fail and count each connection, then set `HTTP_PROXY`, `HTTPS_PROXY`, and `NO_PROXY` to target them before service start. Inject a recording/failing `DialContext` (or resolver) into that production transport solely to prevent external I/O. Exercise one authorized provider-path request and assert `Proxy:nil` (never `ProxyFromEnvironment`), no proxy credential/support configuration, exactly one attempted dial to `api.openai.com:443`, and zero connections to either hostile proxy listener.
5. Prepare a schema-v3 database fixture with representative telemetry, audit, and `event_spikes` records, plus an older-binary package. Record row counts and `PRAGMA user_version`.

**Expected:** dashboard operation works; provider access and automatic investigation are both false by default; the production transport attempts only the fixed OpenAI origin and hostile proxy listeners receive zero connections; no fixture needs an external network connection or real secret.

## 8. Session-drop matrix (US3; SC-005)

Drive distinct accepted reports through the existing lower-tail detector and inspect persisted source/baseline state, eligibility, authenticated REST/SSE, and injected count. Use defaults: 96 per-host local quarter-hour slots, per-host all-hours fallback after 20 eligible normal observations spanning 24 hours, seven eligible local days for a slot, decay, lower-tail `1e-4`, loss 3 and 30%, 2-of-3 confirmation, and 60-minute host cooldown. Candidate, confirmed, drain, and gap observations never train either baseline.

### Durable accepted-report inbox and startup drain

1. Inspect the `sqlite_master` table DDL, `PRAGMA table_info(session_drop_observation_inbox)`, and indexes: `accepted_sequence INTEGER PRIMARY KEY AUTOINCREMENT` is the private global acceptance order, and `UNIQUE(canonical_host, report_epoch_ms)` is the idempotency constraint. Submit accepted reports for distinct synthetic hosts in the same controlled `accepted_at_ms` millisecond. Verify each single SQLite writer transaction persists its `servers.last_result_json` with one inbox insert, assigns distinct contiguous `accepted_sequence` values in commit order, and treats `accepted_at_ms` only as evidence/time—not an ordering key. Redeliver an identical `(canonical_host, report_epoch_ms)` and verify idempotency leaves its one inbox row and sequence unchanged.
2. Stop the detector, accept three distinct rows with the same `accepted_at_ms` (including reports whose report epochs would sort differently), then start draining. Verify the detector drains strictly ascending `accepted_sequence`, not host, report epoch, or acceptance time, and atomically applies each row with its watermark, baseline, and source updates before deleting or marking it consumed. Assert the outcome is exactly that sequence's outcome, with no duplicate score, training, confirmation, or source.
3. Inject controlled crashes after the first and after the final same-millisecond acceptance commit, each before callback/wakeup.
