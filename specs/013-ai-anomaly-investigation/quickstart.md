# Implementation Validation Quickstart: AI Anomaly Investigation (013)

Use this runbook on an isolated Windows dashboard/service test installation with a disposable telemetry database and synthetic reports. It validates the implementation described in [spec.md](./spec.md), [plan.md](./plan.md), and [research.md](./research.md); it is not an operator authorization to send production data to a third party.

## Safety and test fixture rules

- Use an injected `http.RoundTripper` or `http.Client` test double that records the outgoing request while preserving its URL. **Never enter a real provider key** in routine validation and never send customer, host, Event Log, session, credential, or production telemetry data. Production endpoint selection is fixed; do not use a local server, proxy, endpoint override, TLS bypass, or redirect configuration.
- Use synthetic registered-host values that are canaries, not real names (for example `HOSTNAME-CANARY.invalid`), synthetic source IDs, and synthetic aggregate metrics. The injected transport must record only the test request in protected test output and its capture must be deleted after each scenario.
- Run dashboard-group requests with a test dashboard session and machine-account requests with a separate test machine identity. Do not broaden authorization or disable TLS validation to make a test pass.
- Use the supported configuration/update paths and the normal service lifecycle. Do not edit SQLite rows, `config.json`, or DPAPI values by hand except where a migration fixture explicitly creates an old-version database.
- Record only state, counts, IDs, hashes, safe reason enums, and redacted capture assertions. Do not copy a Bearer header, a DPAPI ciphertext, a request body, raw provider response, or an on-disk database into test results.

**Cleanup after every section:** disable provider access and automatic investigation through the dedicated investigation settings route; clear the test credential through its explicit clear operation; discard the injected transport capture; restore the normal test configuration; and delete the disposable database only after any required migration/rollback observation is complete.

## 1. Prerequisites and baseline

1. Build/install the Windows dashboard/service under test and start it with a fresh, disposable `config.json` and SQLite telemetry database. Create a dashboard-group session, a non-dashboard session, and a machine-account client.
2. Prepare fixtures for one confirmed `event_spikes` source and deterministic accepted reports for two synthetic registered hosts. The fixture must retain canonical host only in the deterministic source row; attempts must link with `source_kind` and `source_id` only.
3. Inject a recording `http.RoundTripper`/client test double into the provider client. It must record request count, method, exact URL, redirect attempts, headers (with Bearer value redacted), body byte count, and a body scan for each synthetic forbidden canary; it returns selectable strict responses, failures, delayed responses, and oversized headers/bodies without retaining response prose. Its recorded URL must remain `https://api.typesafe.ai/v1/systemone`; the fixture must not redirect or transmit on the network.
4. Prepare a schema-v3 database fixture containing representative existing telemetry, audits, and `event_spikes`, plus an older-binary test package. Record its row counts and `PRAGMA user_version` before upgrade.

**Expected:** the dashboard is usable; default provider access and automatic investigation are false; no test fixture requires a real secret or external network access.

## 2. Default-disabled and compatibility proof (US1, US4; SC-002)

1. Leave provider access and automatic investigation disabled. Deliver a confirmed synthetic evtspike and drive a valid unexplained session-drop confirmation sequence.
2. Observe the ordinary evtspike source, session-drop source, dashboard source/list/detail views, and any normal evtspike notification fixture.
3. Inspect injected-client count, attempt queue/history, safe provider status, and diagnostics.
4. Exercise existing agent report decoding, `/api/v1/spike`/evtspike consumers, `recent_spike`, `detector_status`, drain behavior, freshness, normal dashboard pages, and the existing shared `GET /api/v1/settings` and machine `GET /api/v1/config` projections.

**Expected:** both deterministic sources remain observable; provider request count is zero; no automatic attempt is queued; evtspike `SpikePayload`, notification behavior, report shapes, existing API/SSE types, shared settings, and machine config are unchanged. Investigation/session-drop additions do not require an old consumer to interpret them. This proves SC-002 and the compatibility portion of SC-008.

## 3. Dedicated settings, DPAPI, consent, and authorization (US4; SC-007)

1. Read `GET /api/v1/investigation/settings` and `GET /api/v1/investigation/status` as a dashboard-group session. Confirm the fixed `typesafe_jev` profile and endpoint metadata, false access/automatic flags, acknowledgement state, validated session-drop settings named `lower_tail_threshold`, `minimum_drop_sessions`, `minimum_drop_percent`, `baseline_half_life_hours`, and `cooldown_minutes`, and `has_credential: false` are visible. Confirm the status state is one of exactly `disabled`, `configured`, `ready`, `automatic_enabled`, `degraded`, or `failing`, and its counts cover retained attempts only.
2. Attempt the same settings/status, source/detail, manual-create, and retry operations as the non-dashboard session and machine account. Also inspect machine `GET /api/v1/config` and existing shared settings.
3. Through the dedicated session-only settings `PUT`, provide a **synthetic non-production credential** with its explicit replace command, persist every required acknowledgement statement, and enable provider access while leaving automatic investigation disabled. Restart/reload the service and re-read safe settings/status. Confirm `configured` means acknowledged access is enabled but the credential is missing or undecryptable, and `ready` means acknowledged, enabled, credentialed, automatic off, and no active provider failure.
4. Send a settings `PUT` with the explicit credential command `{ "operation": "preserve" }`; then send one with the replace command and the synthetic credential; then send one with the explicit clear command. Every settings `PUT` must include a credential command—omitting it is invalid. After each operation, verify only `has_credential` and safe booleans change as appropriate. Inspect persisted configuration only by asserting its protected DPAPI representation exists/changes and is not returned; never print or decrypt the value for the test record.
5. Attempt to enable provider access without the complete acknowledgement, after an explicit credential clear, or with invalid session-drop bounds. Also attempt a settings `PUT` that omits the credential command and attempts to write confirmation, slot-count, or maturity settings; the request must be rejected, and those fixed constants must not be writable.

**Expected:** dedicated routes alone expose safe provider fields; existing settings and machine config contain no provider fields. Unauthorized and machine requests are denied before source lookup, evidence creation, attempt creation, or egress. DPAPI credentials are write-only and preserve/replace/clear correctly; every settings `PUT` has an explicit credential command, and credentials never appear in UI/API/SSE/log/audit/telemetry output. Missing acknowledgement/credential or invalid bounds leaves access disabled or rejects the update. With access enabled but automatic disabled, a confirmed source produces no automatic attempt, while an authorized explicit request remains possible. This covers US4 scenarios 1–3 and SC-007.

## 4. Schema-v3-to-v4 upgrade and rollback (FR-012, FR-027)

1. Start the new service against the schema-v3 fixture. Verify a single additive migration advances `user_version` from 3 to 4 and creates investigation-attempt, session-drop anomaly, and baseline/state tables plus required indexes.
2. Recheck existing v3 row counts and read paths: representative audit, telemetry, and `event_spikes` records must remain readable and unchanged. Confirm no source is backfilled into an attempt and no provider request occurs during migration.
3. Create one synthetic attempt and one session-drop record, then run the approved older binary against the copied test database/configuration. Confirm it can use its pre-existing data while ignoring v4 records; it must not drop v4 tables or send/queue provider work.
4. If the older binary rewrites the copied config, re-upgrade and inspect safe settings. Restore valid provider fields and acknowledgement only through the dedicated route if needed.

**Expected:** v4 is additive and idempotent; existing data and source retention remain intact; no global historical evidence/baseline is reconstructed. Rollback does not downgrade/drop v4 data. After an older config rewrite, provider access remains disabled until valid acknowledged configuration is restored. Preserve the migration fixture until this verification is signed off, then delete it.

## 5. Injected-transport completed manual investigation and privacy capture (US1; SC-001, SC-003)

1. In an injected-transport integration test, enable acknowledged provider access with the synthetic credential using its explicit replace command. Keep automatic investigation off. Use a dashboard-group session to request the confirmed synthetic evtspike manually.
2. Have the injected transport return exactly one `choice` answer for each fixed question—likely cause, impact, evidence sufficiency, and human review—with values in their closed enums, a bounded probability map, and confidence for each answer. Do not return prose. Set the response `model` to separate non-secret canaries representing a credential, canonical host/IP, URL/path, and prose; it is bounded untrusted shape-validation input only.
3. Verify one immutable attempt moves `queued → running → completed`, and inspect source/history/detail as an authorized operator. Confirm it labels output as a hypothesis, separates deterministic source facts from provider hypotheses, records each question's bounded probability map and confidence separately, and records stable source kind/ID, evidence omission summary, timestamps, and only closed local provenance: `provider_profile=typesafe_jev`, `requested_model=jev-latest`, request timing/byte counts, and `validation_outcome=accepted`. Confirm the response `model` canaries are discarded—not persisted, logged, projected, or included in provenance—and that the System One `state` field is a JSON object, not JSON encoded as a string.
4. Inspect the injected transport capture without displaying sensitive bytes: assert one `POST` to exactly `https://api.typesafe.ai/v1/systemone`, normal production TLS behavior, no redirect, a mandatory redacted `Authorization: Bearer` header, one request only, canonical compact `state <= 8,000` UTF-8 bytes, total request `<= 16 KiB`, and fixed four `choice` questions only.
5. Populate every forbidden synthetic canary in the deterministic source/context: canonical host/FQDN/domain/IP/customer-like string, username, session ID, `changed_by`, free text, URL/path, Event Log/XML, dump marker, credential marker, notification-secret marker, and arbitrary-file marker. Scan captured request body and persisted sanitized evidence/result/provenance/error/diagnostic/SSE/browser durable state for all canaries, including each response-`model` canary.
6. Assert evidence source facts are closed and useful: event spikes carry one fixed `channel` code from `agent`, `dashboard`, `eventlog`, `wmi`, `perf`, `service`, `unknown`, or `custom_channel`, window times, observed count, expected count in thousandths, and tail probability in parts per billion; session drops carry observed/reference/expected counts (expected in thousandths), absolute loss, relative loss basis points, tail probability ppb, and classification. Context remains enums. For retained local/fleet samples, exercise and accept every exact closed `metric` enum member—`cpu_pct`, `cpu_p95_pct`, `mem_avail_mb`, `mem_total_mb`, `pages_sec`, `disk_queue`, `tcp_retrans_sec`, `input_delay_p50_ms`, `input_delay_p95_ms`, `input_delay_max_ms`, `session_cpu_p95_pct`, `session_cpu_p50_pct`, `session_mem_p95_bytes`, `session_mem_p50_bytes`, `rfx_fps_out`, `rfx_fps_out_p50`, `rfx_skip_server_sec`, `rfx_skip_net_sec`, `rfx_encode_ms`, `rfx_encode_ms_p50`, `rfx_quality_pct`, `rfx_quality_pct_p50`, `rfx_rtt_ms`, `rfx_rtt_ms_p50`, `rfx_loss_pct`, `rfx_loss_pct_p50`, `rfx_skip_server_sec_p50`, `rfx_skip_net_sec_p50`, `sessions_total`, `sessions_active`, `sessions_disconnected`, and `sessions_max`—with a non-negative integer `value_milli` counter value ×1,000. Reject only a metric outside that enum; never permit floating-point values, arbitrary strings, or a negative value. Where the session metrics are present, retain the relationship check that `sessions_total` is active plus disconnected.
7. Redeliver the same durable spike ten times while its attempt is queued/running, then again after completion.

**Expected:** exactly one root attempt and exactly one injected-client observation exist for the ten redeliveries; queued/running calls return its existing ID and completed source creates none. The request and every provider-bound/derived artifact contain none of the forbidden canaries, while authorized source/list/detail resolves the canonical host only from the deterministic source row. This proves SC-001 and SC-003 and every US1 acceptance scenario. Delete all synthetic captures after recording pass/fail assertions.

## 6. Result strictness, insufficient evidence, lifecycle, and retry (US1, US2)

1. Repeat with each invalid injected-response case: missing/duplicate/fifth question; non-`choice` discriminator (`score` or `noul`); unsupported enum; prose; malformed or unbounded probability map/confidence; over-limit headers; decompressed body over 32 KiB; and error body over 4 KiB.
2. Repeat with required retained evidence deliberately unavailable before send. Verify the stored state is `insufficient_evidence` when SQLite is writable, no result or provenance exists, and no broader data collection or transport invocation occurs.
3. For a valid response whose evidence sufficiency is `insufficient`, verify all four answers are validated but cause/impact choices, probability maps, and confidences are neither persisted nor displayed. Repeat with human review `required` and inspect API/SSE/UI rendering.
4. Attempt to alter terminal result/evidence/provenance rows through the supported store/API path; attempt retry from a completed source; then request a retry from failed and insufficient attempts as an authorized operator. For one retained failed or insufficient predecessor, expire its deterministic source row, then retry as an authorized dashboard user. Verify authorization and predecessor lookup occur first, source lookup returns `404 source_not_found`, and the request creates no evidence, new attempt, provider work, or stale-evidence reuse.

**Expected:** malformed/oversized/nonconforming output is discarded and becomes a safe failed result with no partial classification or raw response retained. Insufficient evidence is explicit and suppresses cause/impact conclusions, probabilities, confidences, recommendations, and actions. Terminal attempts are immutable. Only failed/insufficient attempts whose deterministic source remains retained create a new linked immutable retry with a fresh bounded snapshot; prior attempts remain unchanged. A retained predecessor with an expired source is not retryable and returns `404 source_not_found` without further work. Cleanup by expiring/removing only the disposable fixture data.

## 7. Injected-transport provider-failure lifecycle, disablement, storage failure, and restart interruption (US2, US4; SC-004, SC-006)

1. In injected-transport integration tests at the fixed `https://api.typesafe.ai/v1/systemone` URL, configure cases for connection failure, 30-second timeout, authentication rejection, provider rate limit, upstream failure, redirect refusal, request/response limit, invalid response, and malformed/over-limit output. Run one manual attempt for each; verify a terminal `failed` row with exactly one safe reason from `authentication_failed`, `configuration_disabled`, `configuration_invalid`, `evidence_unavailable`, `interrupted`, `network_error`, `provider_rate_limited`, `redirect_refused`, `request_limit`, `response_invalid`, `response_limit`, `storage_unavailable`, `timeout`, or `upstream_error` when SQLite is writable and no automatic HTTP retry. Verify queue full is rejected by the API without an attempt failure, and worker rate limiting delays rather than drops accepted work.
2. Queue an attempt, then disable provider access or invalidate its acknowledgement/credential before worker send. Verify current configuration is checked immediately before send, queued work is cancelled, completed history stays readable, and injected count remains unchanged.
3. Force the attempt-store write to fail before evidence persistence using the isolated test database fault fixture. Verify zero egress and a structured local safe diagnostic; restore writability and verify no invented retroactive send occurs.
4. Place one attempt in durable `running` state through the controlled worker test hook after its single test request has started, stop the dashboard/service, then start it again. Inspect recovery before enabling any send path.
5. During all failures, repeat a normal agent report, deterministic evtspike, drain transition, freshness evaluation, notification fixture, and ordinary dashboard request.

**Expected:** injected-transport integration proves safe provider-failure lifecycles without real network traffic. Each failed path is safe, bounded, and visible without credentials/raw bodies; detection, drains, notifications, normal dashboard operation, and no-remediation policy continue. Pre-crash `running` becomes terminal `failed` with reason `interrupted`, preserves sanitized audit data until expiry, and causes zero automatic resend. No failure triggers commands, PowerShell, restart, drain, notification, configuration change, or remediation. This proves SC-004 and SC-006.

## 8. Session-drop matrix (US3; SC-005)

Drive each case through distinct accepted reports for a synthetic registered host and inspect baseline state, source persistence, provider eligibility, REST/SSE output, and injected-client count. Use the validated defaults: 96 local quarter-hour slots **per host** plus one per-host all-hours fallback, seven distinct eligible local days for slot maturity, all-hours fallback usable only after at least 20 eligible normal observations spanning at least 24 hours, lower-tail `1e-4`, absolute loss 3, relative loss 30%, 2-of-3 confirmation, and 60-minute host cooldown. Both slot and fallback baselines use time decay and reject candidate, confirmed, drain, and gap observations from training.

| Case | Procedure | Expected result |
|---|---|---|
| Mature unexplained drop | Train eligible normal reports over seven distinct eligible local days in one host slot, then supply qualifying 2-of-3 lower-tail losses outside drain context. | One distinct `unexplained` anomaly, canonical host in authorized source/list/detail only, provider-eligible; no notification. |
| Per-host all-hours fallback | For host A, train 20 eligible normal observations spanning at least 24 hours without maturing the tested slot; supply a qualifying confirmation. Repeat on untrained host B and inspect both baseline records. | Host A's all-hours fallback can score; host B cannot borrow it. The fallback is per-host, never fleet-pooled. |
| Drain overlap | Repeat qualifying confirmation while any drain is non-`AllowAll`. | Persist `drain_associated`; do not train/lower slot or all-hours baseline and do not make provider eligible. |
| Post-drain horizon | Confirm within one confirmation horizon after a non-`AllowAll` drain ends. | Same `drain_associated`/ineligible outcome. |
| Unknown context | Keep freshness affirmatively `fresh`, but omit drain or other detector-classification context at confirmation. | Persist `unknown_context`; not provider eligible; no invented context. |
| Unknown/stale freshness or unavailable observation | Supply unknown freshness, then stale freshness, nil enumeration, invalid values, and unavailable telemetry. | Unknown gap: confirmation breaks, no baseline training or scoring, no numeric-zero conversion, and no anomaly. |
| Out-of-order/duplicate | Deliver duplicate and lower epoch accepted reports. | Persist the exact `duplicate_report_epoch` gap enum; no double score, baseline training, or anomaly. |
| Numeric zero | Deliver a successful enumeration whose active plus disconnected total is zero. | Valid numeric observation, not a nil/gap substitution; normal threshold/confirmation rules still apply. |
| Candidate/confirmed poisoning | Feed candidate then confirmed values and inspect subsequent slot and all-hours baselines. | Neither candidate nor confirmed value trains or lowers either baseline. |
| Immature/within-threshold/rise | Use fewer than seven slot days and fewer than 20 normal observations/24 hours for fallback, stable/rising data, or loss below required tail/minimum. | No anomaly. |
| Cooldown/restart | Confirm once, repeat within 60 minutes, restart service, then repeat after cooldown. | No duplicate during cooldown; persisted order/bases/cooldown survive restart; later eligible observation can be scored. |

**Expected:** only the valid confirmed unexplained case is provider-eligible. Verify the injected provider client stays at zero unless an authorized request/automatic configuration intentionally starts a test attempt. This proves all US3 scenarios and SC-005; remove synthetic baseline/anomaly rows with the disposable database after validation.

## 9. Production dashboard browser fixture (US1–US4; SC-007)

1. Start the production-built dashboard frontend in a real browser against an in-process dashboard harness. Seed it only with synthetic deterministic sources, session-drop anomalies, attempt history, and dashboard/non-dashboard/machine test identities. Inject the recording fixed-URL `http.RoundTripper` into the harness provider client; it must retain `https://api.typesafe.ai/v1/systemone` and never use an endpoint override, proxy, redirect, real credential, or real TypeSafe call. The injected provider transport must not transmit on the network. This is an integration surface, not a JavaScript unit-test or mocked-component framework.
2. As a dashboard-group identity, navigate the rendered production pages for settings/status, source history/detail, session-drop list/detail, manual create, and retry. Confirm authorization happens before lookup/build/create; deterministic source projections alone may resolve the synthetic canonical-host canary, while investigation history remains host-free.
3. Use the visible manual-create control for an eligible evtspike and observe its rendered lifecycle through the live existing SSE connection: queued/running state, one completed hypothesis, source kind/ID, and safe status/count fields must appear only after the harness has durably written them. Make the injected transport return the fixed valid four-choice result and confirm the UI separates observed source facts from the completed provider hypothesis.
4. In separate browser scenarios, seed or return: provider insufficiency, local insufficiency before send, human review required, a safe provider failure, and a failed or insufficient terminal attempt. Verify provider/local insufficiency suppresses cause/impact conclusions; human-review suppression shows no autonomous action controls; failure exposes only a safe reason; and retry is visibly enabled only for failed/insufficient eligible attempts. Use the retry control and observe its new linked lifecycle over SSE.
5. Exercise manual create and retry for disabled, ineligible, completed, unknown, non-dashboard, and machine requests. Verify the rendered UI gates unavailable actions by eligibility/state, and direct safe route errors neither disclose source/provider details nor create an attempt or provider request. Confirm the browser safely ignores additive SSE event types it does not understand.
6. Inspect rendered UI, SSE payloads, browser-local durable state, and injected capture using redacted assertions only. They must contain no canonical-host canary outside permitted deterministic source views, credential, raw provider response, arbitrary diagnostic, evidence payload, result/provenance payload, or forbidden synthetic canary. Confirm the capture records only deliberately requested fixed-URL sends and no redirect.

**Expected:** the real browser observes production frontend behavior end-to-end against the in-process synthetic harness: allowed manual creation, live attempt SSE, completed hypothesis, provider/local insufficiency, human-review suppression, safe failure, state-gated retry, and safe authorization/route errors. This fixture proves UI behavior without a real TypeSafe call or a fictitious JavaScript test framework. The installed Windows smoke remains the separate zero-network/default-disabled check in section 11 and must not inject a transport or exercise provider work.

## 10. Retention and rollback proof (US2, US4)

1. Set a short **test-only** `AuditDays` value through supported test configuration. Create attempts with controlled `created_at` values on both sides of the cutoff, including evidence/result/provenance and retry lineage; create session-drop sources with controlled `detected_at`; and create independent source spike and baseline fixtures.
2. Run the retention worker once and inspect the maintenance-job outcome, deleted attempt count, remaining rows, and source/baseline records.
3. Confirm each attempt expires independently from its own `created_at`, deletes only its own evidence/result/provenance, and leaves `retry_of_attempt_id` as an opaque integer when its predecessor has expired. A newer retry must not retain its expired predecessor. Confirm session-drop sources use independent `AuditDays` retention from `detected_at`, while baselines persist for registered hosts and are deleted only on permanent server removal.
4. Repeat the rollback sequence in section 4 after retention. Confirm old code ignores additive tables and no downgrade deletes them or creates egress.

**Expected:** only expired investigation attempts and their own dependent artifacts are removed in chunks with a safe maintenance record; deterministic source and session-drop retention are independent, and baseline policy is independent of attempt expiry. Restore the normal test `AuditDays` before further work.

1. Run focused unit and boundary tests for: evidence allowlist/order/limits and closed source facts; fixed four-question decoder with separate bounded probability/confidence persistence; DPAPI preserve/replace/clear and rejection of a settings `PUT` without a credential command; lifecycle/dedupe/queue rejection/worker delay; schema migration/store/independent retention; restart recovery; per-host session-drop slot/all-hours matrix; authorization; API/OpenAPI/SSE/UI reducers; the production-browser/in-process-harness fixture with injected fixed-URL transport; completed manual and safe provider-failure injected-transport integration at the fixed endpoint; and unchanged evtspike/report contracts.
2. Run the repository's required final gates from a clean working tree: `go test ./...`, `just lint`, and configured pre-commit checks. Resolve every failure or warning; do not bypass hooks.
3. On an actual isolated installed Windows dashboard/service, perform a zero-network smoke with synthetic data only and no provider key: start the service; verify default-disabled behavior and deterministic source creation; exercise settings/status with a missing credential; observe the source through REST, SSE, and UI; disable provider access and explicitly clear the credential; restart; and recheck ordinary report/evtspike/dashboard behavior. Do not inject a transport, configure provider access, or request provider work in this smoke.

**Expected:** all gates pass without warnings. The installed Windows dashboard remains usable; its zero-network smoke uses no real TypeSafe key, makes zero provider transmissions, and proves default-disabled behavior, deterministic-source REST/SSE/UI projection, explicit clear, restart, and unchanged ordinary operations. Only injected-transport integration tests prove completed manual and safe provider-failure provider lifecycles, including deliberately requested fixed-URL sends.
